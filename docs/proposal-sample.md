# 기술 제안서 — 제조 현장 사내 AI 플랫폼 구축 (가상 RFP)

> **가상 고객**: 중견 자동차 부품 제조사 / **작성**: 이장한 (AX Platform Lab 사이징 계산기·실측 기반) / 2026-10-08
> 모든 수치는 **공식 기반 근사치**이며, 제품 가격은 다루지 않는다. 최종 구성은 PoC 실측으로 확정한다.

## 2. 요구사항 정량화
| 항목 | 가정 | 값 | 근거 |
|---|---|---|---|
| 동시 생성 요청 | 동시 사용자 × 활성 비율 30% | **30건** | 화면을 연 사람이 모두 같은 순간 답변을 생성하지는 않음. PoC 로그로 보정 |
| 요청당 컨텍스트 | RAG 근거 5청크 + 질문 + 답변 | **4,096 토큰** | 프로젝트 M4 프롬프트 구성 |
| 모델 | 한국어 성능을 고려한 30B급 공개 모델, FP8 | **32B FP8** | 3B 실측에서 근거 없는 답변 시 환각 확인 → 상위 모델 필요. 14B 대안도 PoC 비교 |
| 문서 | 2만 건 × 평균 10쪽 | 청크 **50만 개** | 700자 청크, 100자 겹침 |
| 일 질의 | 사용자 800명 × 평균 2.5회 | **2,000건/일** | 감사 로그·백업 산정 |

## 3. 제안 아키텍처

```
           ┌───────────── 관리망 (iDRAC/BMC, 1GbE) ─────────────┐
 사용자 ── 서비스망(25GbE) ── [L4 LB] ── 입구(Ingress, TLS·사내 CA)
                                         │
        ┌──────────────── 쿠버네티스 (OpenShift 또는 RKE2, 컨트롤 플레인 3대) ───────────────┐
        │  GPU 서버 #1  L40S ×4 : LLM 레플리카 A (TP2) · 임베딩 · 여유 1                        │
        │  GPU 서버 #2  L40S ×4 : LLM 레플리카 B (TP2) · 리랭커/에이전트 · 여유 1 (→ 비전 AI)    │
        │  앱 노드 ×2   : 게이트웨이(권한·감사), 웹, 모니터링                                    │
        │  데이터 노드 ×3: PostgreSQL+pgvector HA (EDB/CloudNativePG), MinIO 분산(이레이저 코딩) │
        └──────────────────────────────── 스토리지망(25GbE) ─────────────────────────────────┘
                                         │
                 백업: Veeam → 엑사그리드(불변 보관) + 오프사이트 사본
```

| 영역 | 제안 | 이유 |
|---|---|---|
| **GPU 서버** | L40S 48GB × 4장 서버 **2대** (예: Dell PowerEdge 2U GPU 서버급) | 32B FP8 + 동시 30건 = 70.6GB → **L40S 2장(TP2)이면 레플리카 1벌**. 2대에 1벌씩 두면 **한 대가 고장 나도 서비스 유지**. 남는 GPU로 임베딩·에이전트·비전 AI 시작 |
| 대안 | H100 80GB × 2 | 1장에 1벌이 들어가지만 70.6/72GB로 여유가 없다 → 동시 요청 증가·긴 컨텍스트에 취약. 장기적으로 대형 모델이면 H200(141GB) 검토 |
| 컨테이너 플랫폼 | OpenShift 또는 RKE2, 컨트롤 플레인 3대 HA, **GPU Operator** | 드라이버·device plugin·DCGM 모니터링을 노드 추가 시 자동 적용 |
| 서빙 | vLLM (OpenAI 호환 API) | 동시 요청 처리량(continuous batching), TTFT·KV 캐시 지표 제공 |
| 데이터 | PostgreSQL + pgvector (HA), MinIO 분산 모드 | 벡터 50만 개·5.3GB 규모는 pgvector로 충분. **RDB의 권한·RLS·백업 체계를 그대로 사용** |
| 네트워크 | 관리망 / 서비스망 / 스토리지망 분리, Spine-Leaf | 추론 위주라 GPU 간 InfiniBand는 불필요(서버 내 TP는 PCIe). 학습 도입 시 재검토 |
| 보안 | 사내 SSO(AD) 연동, 문서 ACL 동기화, 앱 필터 + DB RLS 두 겹, 감사 로그, NetworkPolicy 기본 거부 | 프로젝트 M4·M5에서 검증한 구조 |
| 백업 | DB 물리 백업 + WAL(PITR), 원본 문서·모델 버전 보관, **불변 저장소**, 오프사이트 | 랜섬웨어 대응, RPO 분 단위 |

## 4. 사이징 근거 (사이징 계산기 결과)
| 구성요소 | GB | 계산 |
|---|---|---|
| 가중치 (32B × 1바이트) | 32.0 | FP8 |
| KV 캐시 (2 × 64레이어 × KV헤드 8 × 128 × 2바이트 × 4,096 × 30건) | 32.2 | 동시 요청에 비례 |
| 런타임 여유 10% | 6.4 | |
| **합계** | **70.6** | L40S 가용 43.2GB → **2장 텐서 병렬** |

| 항목 | 값 |
|---|---|
| 벡터DB | 청크 50만 개, 벡터 2.05 + 인덱스 2.18 + 본문 1.05 = **약 5.3GB** → DB 서버 메모리 32GB 이상 권장(HNSW 상주) |
| 최초 임베딩 | CPU 기준 약 63시간(프로젝트 실측 속도 외삽) → **GPU 임베딩 서빙으로 구축 기간 내 처리** |
| 감사 로그 | 연 약 1.1GB (2,000건/일 × 1.5KB) → 규정 보관 기간에 맞춰 보관 |
| 백업 | DB·감사 로그 일 1회 × 7개 ≈ 22GB + 원본 문서·모델 파일 별도 |

> **KV 캐시가 가중치만큼 크다.** GPU 대수를 결정하는 것은 모델 크기보다 **동시 사용자 수와 컨텍스트 길이**다. 동시 요청이 2배가 되면 KV 캐시도 2배가 된다.

| 1. 인프라 | 3주 | 서버 랙 실장, BMC·OS·드라이버, 쿠버네티스·GPU Operator, 네트워크 분리 | 인수 테스트 결과(DCGM 진단) |
| 2. 플랫폼 | 3주 | 서빙·DB·스토리지·입구·모니터링·백업, **폐쇄망 반입 설치** | 설치 절차서, 모니터링 대시보드 |
| 3. RAG 서비스 | 3주 | 문서 수집(파싱·청크·임베딩), 권한 연동, 게이트웨이·화면 | 권한 자동 테스트 결과 |
| 4. 안정화·이관 | 2주 | 부하·장애 훈련, 복구 훈련, 운영자 교육 | 런북, 복구 훈련 보고서 |
| 5. 확장 | 이후 | 설비 이상 대응 에이전트 → 외관 검사 비전 AI | 단계별 PoC |

## 6. PoC 계획 (2~4주)
| 항목 | 방법 | **성공 기준** |
|---|---|---|
| 답변 품질 | 현업과 함께 만든 질문 100개(정답·근거 문서 포함) | 근거 문서 적중 **80% 이상**, 근거 없는 질문 "모름" 응답 **90% 이상** |
| 권한 | 부서별 대표 계정으로 같은 질문 → 범위 비교 자동 테스트 | 권한 밖 문서 노출 **0건** (100% 통과) |
| 성능 | 동시 30건 부하 | TTFT p95 **3초 이내**, 오류율 **1% 미만** |
| 폐쇄망 설치 | 반입 번들로 재구축 | **1일 이내** 재구축, 외부 통신 0 |
| 복구 | DB 백업 복구 훈련 | RTO **1시간 이내**, RPO **15분 이내**(PITR 적용 시) |
| 모델 선택 | 14B vs 32B, FP8 vs INT4 같은 질문 세트로 비교 | 품질·지연·GPU 수 트레이드오프 표로 결정 |

## 7. 운영·장애 대응 체계 (IT 운영 3명 기준)
- **자동 감시**: GPU(온도·메모리·Xid), TTFT·대기열, 5xx, 권한 거부 급증, 백업 미성공, Job 실패 알람을 심각도별로 메신저 연동
- **런북**: OOM, 모델 이름 오류, GPU Pending, DB 장애, 임베딩 교체, 요청 폭주, 권한 필터 사고, 데이터 유실 (프로젝트 `runbooks/01~08`을 고객 환경에 맞게 이관)
- **역할 분담**: 1차(고객 IT) 알람 확인·런북 1단계 / 2차(구축사 기술지원) 원인 분석·조치 / 3차(벤더) 하드웨어·드라이버
- **정기 작업**: 월 1회 복구 훈련 결과 확인, 분기 1회 장애 훈련, 감사 로그 월간 리포트, 모델·문서 업데이트 절차(반입 → 스테이징 평가 → 배포)

| 운영 인력 부족 | 장애 대응 지연 | 자동 감시·런북·유지보수 계약(SLA), 운영 교육 |
| GPU 공급 리드타임 | 확장 지연 | 확장 단계 GPU를 미리 계획, 대안 GPU(H100/H200) 사이징 병행 |

## 9. 온프레미스 vs 클라우드 LLM API (판단 기준)
| 기준 | 온프레미스 GPU (제안) | 클라우드 LLM API |
|---|---|---|
| 보안·망분리 | **폐쇄망 요구 충족**, 데이터 외부 전송 없음 | 외부 전송 필요 → 이번 RFP 조건 불충족 |
| 비용 구조 | 초기 투자 + 전력·운영, 사용량이 많을수록 유리 | 사용량 비례, 초기 부담 낮음 |
| 확장성 | 증설에 조달 기간 | 즉시 |
| 모델 | 공개 모델, 사내 데이터로 튜닝 가능 | 최신 대형 모델 |
| 운영 | 플랫폼 운영 역량 필요 → 런북·자동화·기술지원으로 보완 | 운영 부담 낮음 |

**결론**: 폐쇄망 필수 조건 때문에 온프레미스가 유일한 선택지다. 동시 30건 기준 32B FP8은 **L40S 2장으로 1벌**이 들어가므로, **4장 서버 2대**로 이중화하면서 남는 GPU로 확장 단계를 시작할 수 있다. 최종 모델 크기와 GPU 수는 PoC의 품질·지연 측정으로 확정한다.
