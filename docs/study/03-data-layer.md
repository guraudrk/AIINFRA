# 03. 데이터 계층 — 스토리지, 벡터DB, 수집 파이프라인

## 한 줄 요약
가상 제조사 한빛정밀의 문서 18개와 정형 데이터 7종을 만들었다. 원본은 MinIO(S3 호환)에, 청크 138개와 1024차원 임베딩은 PostgreSQL+pgvector에 data 노드 StatefulSet으로 올렸고, "MinIO → 청크 → 임베딩 → pgvector" 수집 파이프라인을 Job/CronJob으로 자동화했다.

## 용어 풀이 (비전공자용)
> 비유 기준: 클러스터 = 병원. 이번에는 병원의 **기록 보관실(data 노드)**에 **원본 서류 창고(MinIO)**와 **색인 카드 서랍(pgvector)**을 만들었다.

### 스토리지 종류
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **블록 스토리지** | 디스크를 일정한 크기의 칸(블록)으로 쪼개 OS에 "빈 디스크"로 붙여 주는 방식. DB처럼 빠른 읽기·쓰기에 쓴다(SAN, EBS) | 아무것도 안 그려진 **빈 공책**. 어떻게 쓸지는 쓰는 사람 마음 |
| **파일 스토리지** | 폴더·파일 구조로 여러 서버가 같이 쓰는 방식(NAS, NFS) | 여러 부서가 같이 쓰는 **공용 서류함** |
| **오브젝트 스토리지** | 파일을 "객체"로 통째로 저장하고 주소(키)로 꺼내는 방식. 용량을 거의 무한히 늘릴 수 있고, 백업·원본 보관·AI 학습 데이터에 쓴다(S3, MinIO) | **택배 물류창고**. 송장 번호(키)만 있으면 찾는다 |
| **S3 / S3 호환** | S3는 아마존의 오브젝트 스토리지이고, 그 API(사용 규칙)가 업계 표준이 됐다. MinIO는 같은 규칙을 쓰는 설치형 제품이라 S3용 코드가 그대로 돈다 | 국제 표준 **택배 송장 양식** |
| **버킷 (Bucket)** | 오브젝트 스토리지의 최상위 보관 단위. 이번에 `raw-docs`(원본), `backups`(백업)를 만들었다 | 창고 안의 **구역** |
| **MinIO** | 회사 안에 직접 설치하는 S3 호환 오브젝트 스토리지. 에티버스가 총판한다 | **사내 물류창고** |

### 쿠버네티스 저장소
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **PV / PVC** | PV는 실제 디스크 한 덩어리, PVC는 Pod가 "디스크 5GB 주세요"라고 내는 요청서 | **사물함 / 사물함 신청서** |
| **StorageClass** | PVC 요청이 오면 어떤 종류의 디스크를 어떻게 만들지 정한 규칙. kind는 노드 로컬 디스크(local-path), 운영은 외부 스토리지(CSI) | 사물함 **공급 업체와 규격** |
| **CSI** | 쿠버네티스가 외부 스토리지(Dell PowerScale, NetApp 등)를 쓰기 위한 표준 플러그인 규격 | 어떤 업체 사물함이든 끼울 수 있는 **표준 규격** |
| **StatefulSet** | 이름(postgres-0)과 전용 디스크가 고정된 Pod를 관리. 재시작해도 같은 이름, 같은 디스크로 돌아온다 | **지정 병실 + 전용 차트**가 있는 장기 입원 환자 |
| **volumeClaimTemplates** | StatefulSet이 Pod마다 PVC를 자동으로 만들어 주는 틀(data-postgres-0) | 입원 환자마다 사물함 **자동 배정** |
| **Secret** | 비밀번호 같은 민감한 값을 따로 보관하는 쿠버네티스 객체. 코드나 Git에 비밀번호를 쓰지 않는다 | **금고**. 필요한 사람에게만 열쇠를 준다 |
| **ConfigMap** | 설정 파일이나 작은 데이터를 담는 객체. 이번에 DB 초기화 SQL과 원본 문서 묶음을 넣었다 | 공용 **게시판** |
| **CronJob** | 정해진 시각마다 Job을 자동 실행(이번에는 30분마다 변경분 수집) | 매일 정해진 시간의 **정기 순찰** |

### 벡터DB와 RAG 데이터
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **벡터DB / pgvector** | 숫자 목록(벡터)을 저장하고 "가장 비슷한 벡터"를 빠르게 찾는 DB. pgvector는 PostgreSQL에 그 기능을 더하는 확장 | 도서관의 **좌표 기반 색인 서랍** |
| **청크 (Chunk)** | 긴 문서를 검색하기 좋은 크기로 자른 조각. LLM에 문서 전체 대신 관련 조각만 넣는다 | 책 전체 대신 **필요한 페이지만 복사** |
| **청크 크기 / 겹침 (overlap)** | 조각 하나의 최대 길이(700자)와, 이웃 조각끼리 겹치는 길이(100자). 겹침이 있어야 경계에 걸친 문장이 잘리지 않는다 | 페이지를 복사할 때 **앞 페이지 마지막 줄을 같이** 복사 |
| **코사인 유사도 / 거리** | 두 벡터의 방향이 얼마나 비슷한지(1에 가까울수록 비슷). pgvector의 `<=>`는 "1 - 유사도" = 거리 | 두 화살표가 **같은 쪽을 가리키는 정도** |
| **HNSW 인덱스** | 모든 벡터와 일일이 비교하지 않고, 이웃끼리 연결한 그래프를 따라가며 비슷한 벡터를 빠르게 찾는 근사 검색 색인 | 전국 주소를 다 뒤지지 않고 **"시 → 구 → 동" 순으로 좁혀 가기** |
| **메타데이터** | 문서에 대한 정보(문서ID, 부서, 접근 등급, 버전). 검색 결과를 권한·설비로 거를 때 쓴다 | 서류 표지의 **분류 스티커** |
| **온톨로지** | 데이터끼리의 관계를 정의한 것. 이번에는 "설비 ↔ 경보 코드 ↔ 부품 ↔ 문서" 관계 테이블을 만들었다 | 서류들 사이의 **연결 지도** |
| **수집 파이프라인 (Ingest)** | 원본을 가져와 → 자르고 → 벡터로 바꾸고 → DB에 넣는 자동화 흐름 | 새 책이 오면 **분류 → 색인 카드 작성 → 서랍에 꽂기** |
| **content hash (해시)** | 파일 내용의 지문. 지문이 같으면 안 바뀐 것이므로 다시 처리하지 않는다 | 서류 **봉인 번호**. 같으면 열어 볼 필요 없음 |
| **digest 고정** | 이미지를 태그(latest) 대신 내용 지문(sha256)으로 지정. 누가 같은 태그로 바꿔 올려도 영향받지 않는다 | 상품명 대신 **일련번호**로 주문 |

### DB 권한
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **역할 (Role)** | DB 사용자 계정. 관리자(postgres), 수집용(ax_ingest), 앱용(ax_app)을 나눴다 | 직원별 **출입증** |
| **최소 권한 원칙** | 필요한 권한만 준다. 앱은 읽기 + 감사 로그 쓰기만, 수집은 문서 테이블 쓰기만 | 출입증으로 **필요한 방만** 열린다 |
| **GRANT / TRUNCATE** | GRANT는 권한을 주는 SQL. TRUNCATE(테이블 통째로 비우기)는 DELETE와 **별개 권한**이다 | 서류 한 장씩 버리기(DELETE)와 **서랍째 비우기(TRUNCATE)**는 다른 결재 |
| **트랜잭션** | 여러 작업을 "전부 성공 아니면 전부 취소"로 묶는 것. 적재 중 실패하면 반쯤 지워진 상태가 남지 않는다 | **계약서 일괄 서명**. 하나라도 빠지면 무효 |

## 핵심 개념
- **스토리지는 용도별로 고른다.** DB(PostgreSQL)는 빠른 랜덤 읽기·쓰기가 필요해서 블록 스토리지, 원본 문서와 백업은 많이 쌓이고 통째로 읽으니 오브젝트 스토리지가 맞다. 그래서 원본은 MinIO, 검색용 청크·벡터는 pgvector로 나눴다. 원본이 따로 있으니 청크 전략을 바꾸거나 임베딩 모델을 바꿀 때 언제든 다시 만들 수 있다.
- **RAG 검색은 "문장 → 벡터 → 가까운 벡터 찾기"다.** 같은 임베딩 모델로 문서 청크와 질문을 둘 다 벡터로 바꾸고, 코사인 거리가 가까운 청크를 찾는다. 그래서 **문서와 질문은 반드시 같은 모델**로 임베딩해야 하고, 모델을 바꾸면 전부 다시 임베딩해야 한다.
- **벡터 저장 용량 ≈ 청크 수 × 차원 × 4바이트 + 인덱스.** 이번에는 138 × 1024 × 4B ≈ 0.56MB(벡터만)이었고, 실제 chunks 테이블은 본문 포함 약 2.0MB, HNSW 인덱스는 약 1.1MB였다. 문서 2만 건이면 청크가 수십만 개라 수 GB 단위가 되고, HNSW는 메모리에 올라가야 빠르다(M9 사이징).
- 비유: MinIO는 **원본 서류 창고**, pgvector는 **색인 카드 서랍**이다. 색인 카드(청크 + 좌표)가 망가져도 창고에 원본이 있으니 다시 만들 수 있다. 반대로 창고(원본)를 잃으면 복구할 길이 없어서 **백업 대상 1순위는 원본과 DB**다(M7).

## 이 프로젝트에서 내가 한 것
- `scripts/gen_data.py`(seed 고정): 설비 매뉴얼 10개(프레스·CNC 각 5대, 경보 코드 8개씩), 사내 규정 3개, 품질 불량 보고서 5개, 정비 이력 200건, 부품·재고·관계 CSV를 생성했다. 3호기는 기준 압력 21MPa(다른 호기 18MPa)와 최근 E-203 반복 이력 4건, 관련 품질 클레임(QR-2026-003)으로 서로 맞물리게 만들었다. 압력 센서 재고는 일부러 0개로 넣었다(M4 에이전트 시나리오용).
- 접근 등급을 설계했다. public 3개(규정), maintenance 10개(매뉴얼), quality 5개(품질 보고서). M4 역할별 응답 차이의 근거가 된다.
- **PostgreSQL 17 + pgvector 0.8.7**을 data 노드에 StatefulSet + PVC로 올렸다. 스키마는 문서·청크(vector(1024), HNSW 코사인 인덱스), 정형 6개, 관계 2개, 감사 로그 테이블이다. DB 역할은 3개로 나눴다(postgres / ax_ingest / ax_app, 둘 다 superuser·BYPASSRLS 없음).
- 비밀번호는 `scripts/create-secrets.sh`가 `openssl rand`로 만들어 Secret에 넣고, 이미 있으면 덮어쓰지 않는다. 초기화 SQL은 환경변수(psql `-v`)로만 비밀번호를 받는다.
- **MinIO**: Docker Hub의 `minio/minio` 저장소가 404(삭제), quay.io는 401이었다. 커뮤니티 공식 이미지 배포가 중단된 걸 확인했다. 대안 4개(bitnamilegacy, Chainguard, 커뮤니티 포크, SeaweedFS/Garage)를 비교해서, 소스에서 빌드하고 계속 유지되는 **Chainguard MinIO를 digest로 고정**했다(RELEASE.2026-09-22).
- `apps/ingest`(Python, boto3 + psycopg): upload / structured / docs 모드. 청크는 **제목(##, ###) 단위**로 잘라서 경보 코드 하나의 원인·조치·부품이 한 조각에 담기게 했다. 700자가 넘으면 100자 겹침으로 나누고, 각 청크 앞에 `[문서 제목 > 섹션]` 맥락을 붙였다. 문서 하나 단위로 트랜잭션을 걸어 교체하고, 내용 해시가 같으면 건너뛴다. 임베딩 차원이 설정과 다르면 즉시 실패한다(M8 시나리오 5 대비).
- 실행 결과: 정형 7개 테이블(설비 10, 경보 16, 부품 19, 재고 19, 정비 이력 200, 관계 22·85행), 문서 18개 → **청크 138개**(maintenance 101, quality 25, public 12), 수집 전체 1분 17초(임베딩 약 63초, CPU). 두 번째 실행은 18개 모두 skipped.
- **검색 검증** (`scripts/search-test.sh`):
  | 질의 | 1위 | 2위 | 3위 |
  |---|---|---|---|
  | "E-203" | QR-2026-003 (quality) 0.525 | MAN-PRESS-04 E-203 0.544 | MAN-PRESS-03 E-203 0.544 |
  | "3호기 유압 압력이 떨어졌어요" | QR-2026-003 원인 분석 0.276 | MAN-PRESS-03 E-203 0.363 | MAN-PRESS-03 특이사항 0.385 |
  - **발견 1**: 코드만 검색하면 4호기 매뉴얼이 3호기보다 위에 나왔다. 프레스 5대의 E-203 섹션이 거의 같아서 벡터만으로는 호기를 구분하지 못한다. M4에서 "3호기"를 메타데이터(equipment_id) 필터로 걸어야 하는 근거다.
  - **발견 2**: 품질팀 전용 보고서가 두 질의 모두 1위였다. 권한 필터가 없으면 작업자에게도 그대로 노출된다는 증거다(M4 권한 통제의 이유).
- **겪은 문제 3가지**:
  1. MinIO 공식 이미지 배포 중단 → 대안 비교 후 digest 고정 (위 설명)
  2. 수집 Job이 `permission denied for table alarm_documents`로 실패. 로그를 보니 `TRUNCATE`에서 막혔다. **TRUNCATE는 DELETE와 별도 권한**인데 빠뜨렸던 것이다. 실행 중인 DB에 GRANT를 추가하고, 초기화 SQL도 같이 고쳤다(초기화 SQL은 처음 설치할 때만 돌기 때문).
  3. 위 실패가 몇 초 만에 났는데 스크립트는 10분을 기다렸다. `kubectl wait --for=condition=complete`는 **Job이 실패해도 멈추지 않는다**. 그래서 성공과 실패를 둘 다 감시하다가 실패하면 즉시 로그를 보여 주는 함수로 바꿨다.

## 실제 기업 환경에서는
- **GPU 클러스터 스토리지는 보통 3층**이다. ① 고성능 병렬 파일시스템(학습 데이터, 체크포인트: Dell PowerScale, DDN, WEKA, Lustre), ② 오브젝트 스토리지(원본·모델·백업 보관: MinIO AIStor, Dell ECS), ③ 블록 스토리지(DB). 추론·RAG 중심이면 ②와 ③의 비중이 크다.
- MinIO 운영은 **분산 모드**(4노드 이상, 이레이저 코딩으로 디스크·노드 장애를 견딤)로 구성하고, 버전 관리와 **객체 잠금(Object Lock, 불변 백업)**을 켠다. 기업 고객은 기술 지원과 보안 패치가 있는 상용판(AIStor)을 쓰는 게 일반적이다.
- PostgreSQL은 운영에서 **HA 구성**(Patroni, CloudNativePG 오퍼레이터, EDB Postgres)으로 주/대기 복제를 두고, 쿠버네티스에서는 오퍼레이터가 장애 전환·백업을 자동화한다.
- 벡터 수가 수천만 개를 넘으면 전용 벡터DB(Milvus 등)나 인덱스 튜닝(HNSW `m`·`ef_search`, 양자화)을 검토한다. 수백만 개 이하면 pgvector로도 충분한 경우가 많고, 기존 RDB의 권한·백업·트랜잭션을 그대로 쓸 수 있는 게 큰 장점이다.
- 실제 문서는 PDF·한글(HWP)·스캔 이미지라서 파싱(OCR, 표 추출)이 수집 파이프라인에서 가장 손이 많이 간다. 문서 권한은 원천 시스템(그룹웨어, ECM)의 ACL을 그대로 가져와 메타데이터로 붙인다.

## 에티버스그룹 사업과의 연결
에티버스는 **MinIO 총판**이자 **EDB(PostgreSQL)** 총판이다. 이번 데이터 계층이 정확히 그 두 제품의 조합(원본은 S3 호환 오브젝트 스토리지, 벡터·메타데이터는 PostgreSQL)이다. 커뮤니티 이미지 배포가 중단된 걸 직접 겪어 보니, 기업 고객에게 상용 지원판을 제안하는 이유(보안 패치, 기술 지원, 장기 유지보수)를 실감할 수 있었다.

## 예상 면접 질문 5개 + 모범 답변

**Q1. 블록, 파일, 오브젝트 스토리지의 차이와 AI 플랫폼에서의 용도를 설명해 주세요.**
> 블록은 디스크를 블록 단위로 OS에 그대로 붙여 주는 방식이라 DB처럼 빠른 랜덤 읽기·쓰기에 쓰고, 파일은 NAS처럼 폴더 구조로 여러 서버가 공유할 때 쓰고, 오브젝트는 파일을 키로 통째로 저장해서 용량을 거의 무한히 늘릴 수 있어 원본 데이터나 백업에 씁니다. 제 프로젝트에서는 원본 문서는 S3 호환인 MinIO에 두고, 검색용 청크와 벡터는 PostgreSQL에 블록 스토리지로 뒀습니다. 학습까지 하는 GPU 클러스터라면 여기에 고성능 병렬 파일시스템이 추가된다고 알고 있습니다.

**Q2. RAG에서 문서를 왜 청크로 자르고, 크기와 겹침은 어떻게 정했나요?**
> LLM 컨텍스트에 문서 전체를 넣을 수 없고, 넣더라도 관련 없는 내용이 섞이면 답이 흐려지니까 관련 조각만 찾아서 넣으려고 자릅니다. 저는 글자 수로만 자르지 않고 매뉴얼의 제목 단위, 그러니까 경보 코드 하나 단위로 잘랐습니다. 그래야 원인, 조치, 부품이 한 조각에 같이 들어가거든요. 그래도 길면 700자 단위로 100자씩 겹쳐서 경계 문장이 안 잘리게 했고, 조각마다 앞에 문서 제목과 섹션 이름을 붙여서 조각만 봐도 어떤 설비 내용인지 알 수 있게 했습니다.

**Q3. 벡터DB 저장 용량은 어떻게 계산하나요?**
> 벡터만 보면 청크 수 곱하기 차원 수 곱하기 4바이트(float32)입니다. 제 경우 청크 138개에 1024차원이라 약 0.56MB였고, 실제 테이블은 본문까지 2MB, HNSW 인덱스가 1.1MB 정도 나왔습니다. 고객사 문서가 2만 건이고 문서당 청크가 수십 개면 수십만 청크라 벡터만 수 GB가 되고, HNSW 인덱스는 메모리에 올라가야 빨라서 DB 서버 메모리도 같이 잡아야 합니다. 이 계산식은 사이징 계산기에도 넣을 계획입니다.

**Q4. 의미 검색만으로 충분하지 않은 경우가 있나요?**
> 네, 실제로 겪었습니다. "E-203"이라고만 검색했더니 프레스 4호기 매뉴얼이 3호기보다 위에 나왔는데요, 다섯 대 매뉴얼의 E-203 내용이 거의 같아서 벡터로는 구분이 안 된 겁니다. 그래서 호기나 문서 등급처럼 정확히 걸러야 하는 조건은 메타데이터 필터로 처리하고, 경보 코드 같은 고유 기호는 키워드 검색을 같이 쓰는 하이브리드 방식이 필요하다고 판단했습니다. 또 권한 필터 없이 검색하면 품질팀 전용 보고서가 1위로 나와서, 권한 필터도 반드시 검색 단계에서 걸어야 한다는 걸 확인했습니다.

**Q5. 비밀번호 같은 비밀값은 어떻게 관리했나요?**
> 코드나 Git에는 하나도 안 넣었습니다. 스크립트가 openssl로 무작위 비밀번호를 만들어 쿠버네티스 Secret에 넣고, 이미 있으면 덮어쓰지 않게 했습니다. DB 초기화 스크립트도 비밀번호를 환경변수로만 받습니다. DB 계정도 관리자, 수집용, 앱용으로 나눠서 앱은 읽기와 감사 로그 쓰기만 하도록 최소 권한으로 줬습니다. 다만 쿠버네티스 Secret은 기본적으로 base64 인코딩일 뿐이라, 운영이라면 etcd 암호화나 Vault 같은 외부 비밀 관리 도구를 써야 한다고 알고 있습니다.

**보너스 Q. 오픈소스 이미지가 갑자기 사라지면 어떻게 대응하시겠어요?** (실제 겪은 문제)
> 이번에 MinIO 공식 커뮤니티 이미지가 Docker Hub에서 사라진 걸 겪었습니다. 먼저 일시적인 문제인지 확인하려고 Docker Hub API와 pull 오류 메시지를 봤더니 저장소 자체가 404였습니다. 대안으로 동결된 Bitnami 레거시 이미지, 소스에서 계속 빌드하는 Chainguard 이미지, 커뮤니티 포크, 다른 S3 호환 스토리지를 비교했고, 유지보수와 출처 신뢰성을 기준으로 Chainguard를 골라 digest로 고정했습니다. 고객 환경이라면 기술 지원과 보안 패치가 보장되는 상용판을 권하고, 폐쇄망이면 검증된 이미지를 내부 레지스트리에 보관해 두는 게 맞다고 생각합니다.

## 꼬리 질문 3개 + 답변 방향
1. **"StatefulSet과 Deployment + PVC는 뭐가 달라요?"** → StatefulSet은 Pod 이름(postgres-0)과 PVC(data-postgres-0)가 1:1로 고정되고, 순서대로 생성·종료된다. 레플리카를 늘리면 Pod마다 자기 디스크를 갖는다. Deployment는 Pod가 서로 교체 가능한 무상태 앱용이다.
2. **"HNSW 말고 다른 인덱스는요?"** → IVFFlat(군집으로 나눠 일부만 탐색, 빌드 빠름·메모리 적음, 정확도는 데이터 분포 영향)과 HNSW(그래프, 검색 빠르고 정확, 메모리 많이 씀)가 있다. 데이터가 적으면 인덱스 없이 전체 비교도 충분하다.
3. **"온톨로지 테이블은 어디에 쓰나요?"** → "3호기 E-203에 필요한 부품과 재고"처럼 벡터 검색으로는 정확히 못 찾는 관계 질의를 SQL 조인으로 정확하게 답한다. M4 에이전트의 check_stock, query_maintenance 도구가 이 테이블을 쓴다.
