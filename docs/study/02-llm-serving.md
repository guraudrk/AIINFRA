# 02. sLLM·임베딩 서빙 — 모델 크기, 메모리, 성능 지표

## 한 줄 요약
GPU 노드에 Ollama로 sLLM(qwen2.5:3b)과 임베딩 모델(bge-m3, 1024차원)을 Helm 차트로 배포했다. 모델은 사전 적재 Job으로 PVC에 넣고, 동시 요청 1/4/8개에서 TTFT·토큰/초를 측정했다.

## 용어 풀이 (비전공자용)
> 비유 기준: 클러스터 = 병원(M1). 이번에는 병원에 **의사(LLM)**와 **사서(임베딩 모델)**를 배치했다.

### 모델
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **LLM / sLLM** | 문장을 이해하고 만들어 내는 AI 모델. sLLM은 회사 서버나 PC에서 돌릴 수 있게 작게 만든 것(보통 1B~10B) | 종합병원 교수진 vs **동네 의원 원장님** |
| **파라미터 (3B)** | 모델이 학습으로 익힌 숫자의 개수. 3B = 30억 개 | 의사의 **지식량** |
| **추론 (Inference)** | 학습이 끝난 모델에 질문을 넣고 답을 받는 것. 서비스 운영은 대부분 추론이다 | 공부를 마친 의사가 **진료**하는 것 (학습 = 의대 공부) |
| **토큰 (Token)** | 모델이 글을 읽고 쓰는 단위. 대략 단어 조각 하나. 한국어는 한 글자~한 단어 정도 | 의사가 한 번에 **말하는 음절** |
| **컨텍스트 길이** | 모델이 한 번에 볼 수 있는 최대 토큰 수(질문 + 참고 문서 + 답변). 이 프로젝트는 4096 | 진료 중에 한 번에 펼쳐 볼 수 있는 **차트 페이지 수** |
| **양자화 (FP16 / INT8 / INT4)** | 숫자 하나를 저장하는 칸을 줄여 모델을 작게 만드는 기술. FP16=2바이트, INT8=1바이트, INT4=0.5바이트 | 고화질 사진을 **압축 JPG**로 저장. 작아지지만 약간 흐려짐 |
| **Q4_K_M** | Ollama(GGUF 형식)에서 쓰는 4비트 양자화 방식 이름. 중요한 부분은 조금 더 정밀하게 남겨서 평균 약 4.5~5비트 | 중요한 부분만 고화질로 남긴 **스마트 압축** |
| **임베딩 / 벡터** | 문장을 숫자 목록(벡터)으로 바꾼 것. 뜻이 비슷한 문장은 비슷한 숫자가 된다. bge-m3는 숫자 1024개로 바꾼다(1024차원) | 책마다 매기는 **도서관 좌표**. 비슷한 주제는 가까운 서가에 |
| **차원 (Dimension)** | 벡터에 들어 있는 숫자 개수. 저장하는 DB 칸 수와 반드시 같아야 한다 | 좌표가 (x, y)냐 (x, y, z)냐 |

### 서빙과 성능
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **서빙 (Serving)** | 모델을 서버에 올려서 다른 프로그램이 API로 질문할 수 있게 하는 것 | 의사를 진료실에 **배치해서 진료 개시** |
| **서빙 엔진 (Ollama / vLLM / Triton)** | 모델을 메모리에 올리고 요청을 받아 답을 만들어 주는 프로그램. Ollama는 쉽고 가볍고, vLLM은 GPU에서 동시 처리량이 높고, Triton은 여러 종류 모델을 한 서버에서 운영 | 동네 의원 / **대형 병원 외래 시스템** / 종합 검진 센터 |
| **OpenAI 호환 API** | ChatGPT API와 같은 형식의 주소·요청 규칙. 이걸 지원하면 엔진을 바꿔도 앱 코드를 안 고친다 | 어느 병원이든 같은 **진료 의뢰서 양식** |
| **TTFT** | Time To First Token. 질문을 보낸 뒤 **첫 글자가 나올 때까지** 걸린 시간. 사용자가 "반응한다"고 느끼는 기준 | 진료 접수 후 **의사가 첫마디를 할 때까지** |
| **토큰/초 (TPS)** | 첫 글자 이후 초당 몇 토큰을 만들어 내는지. 답이 얼마나 빨리 써지는지 | 의사가 **말하는 속도** |
| **처리량 (Throughput)** | 서버 전체가 초당 만들어 내는 토큰 총량. 동시 사용자가 많을 때 중요 | 병원 전체의 **시간당 진료 건수** |
| **p95** | 100번 중 느린 쪽 5번을 뺀 최댓값. 평균보다 "대부분 사용자의 체감"을 잘 보여 준다 | 100명 중 95명은 **이 시간 안에** 진료받음 |
| **KV 캐시** | 모델이 앞에서 읽은 내용을 다시 계산하지 않으려고 메모리에 저장해 두는 중간 결과. 컨텍스트가 길수록, 동시 요청이 많을수록 커진다 | 진료 중 **메모 해 둔 내용**. 환자가 많고 대화가 길수록 메모장이 두꺼워짐 |
| **동시성 (num_parallel)** | 한 모델이 동시에 처리하는 요청 수. 슬롯마다 KV 캐시를 따로 잡는다 | 의사 한 명이 **동시에 보는 환자 수** |

### 쿠버네티스 배포
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **Helm 차트** | 여러 매니페스트를 변수(values)로 묶은 설치 패키지. 값만 바꿔 같은 구성을 여러 환경에 설치한다 | 진료실 개설 **표준 패키지 + 옵션 체크리스트** |
| **values.yaml** | 차트의 설정값 파일(모델 이름, 메모리, GPU 수 등) | 패키지 **주문서** |
| **PVC / PV / StorageClass** | PVC는 "디스크 10GB 주세요" 요청서, PV는 실제로 할당된 디스크, StorageClass는 디스크를 만드는 방식(kind는 노드 로컬 디스크) | 사물함 **신청서 / 실제 사물함 / 사물함 공급 업체** |
| **WaitForFirstConsumer** | Pod가 갈 노드가 정해진 뒤에 그 노드에 디스크를 만드는 방식. 디스크와 Pod가 다른 노드에 생기는 문제를 막는다 | 환자 병실이 정해진 뒤에 **그 층에** 사물함 배정 |
| **Job** | 한 번 실행하고 끝나는 작업(모델 다운로드). 실패하면 정해진 횟수만큼 재시도 | **일회성 심부름** |
| **probe (startup / readiness / liveness)** | 쿠버네티스가 컨테이너 상태를 주기적으로 검사하는 것. startup = 다 켜졌나, readiness = 손님 받을 준비 됐나, liveness = 살아 있나(아니면 재시작) | 출근했나 / **진료 준비 끝났나** / 쓰러지진 않았나 |
| **EndpointSlice** | Service가 실제로 트래픽을 보낼 Pod 주소 목록. Ready가 아닌 Pod는 ready=false로 표시되고 트래픽을 받지 않는다 | 대표 내선번호에 연결된 **근무 중 상담원 명단** |
| **headless Service / publishNotReadyAddresses** | headless는 대표 IP 없이 DNS가 Pod 주소를 바로 알려 주는 Service, publishNotReadyAddresses는 준비 안 된 Pod도 명단에 넣는 옵션. 이번에 관리용 `-admin` Service로 썼다 | 고객 상담 번호와 별도인 **직원용 직통 번호**(아직 출근 준비 중이어도 연결) |
| **progressDeadlineSeconds** | 새 Pod가 이 시간(기본 600초) 안에 Ready가 안 되면 Deployment가 "배포가 멈췄다"고 표시 | 입주 **마감 기한** |
| **콜드 스타트** | 모델이 메모리에 없는 상태에서 첫 요청이 오면 모델 로딩 시간까지 기다려야 하는 것. 이번 첫 요청은 38.8초 | 아침 첫 손님은 **가게 문 여는 시간**까지 기다림 |
| **환각 (Hallucination)** | 모델이 모르는 내용을 그럴듯하게 지어내는 것 | 모르는데 **아는 척하는 신입** |
| **requests / limits (메모리)** | requests는 배치할 때 보장받는 양, limits는 넘으면 강제 종료(OOMKilled)되는 상한 | 예약한 침대 수 / **넘으면 퇴실** 기준 |
| **OOMKilled** | 메모리 limits를 넘어서 커널이 프로세스를 강제 종료한 것(Exit Code 137). M8 장애 시나리오 1번 | 정원 초과로 **강제 퇴실** |

### GPU 공유
| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **MIG** | Multi-Instance GPU. A100·H100 같은 데이터센터 GPU를 최대 7조각으로 **물리적으로** 나눈다. 조각끼리 메모리·성능이 완전히 격리된다 | MRI실을 **벽으로 나눈** 7개 방 |
| **time-slicing** | GPU 하나를 여러 Pod가 **시간을 나눠** 번갈아 쓴다. 격리는 없고, 메모리를 서로 침범할 수 있다 | MRI 한 대를 **시간대별 예약** |
| **MPS** | Multi-Process Service. 여러 프로세스가 GPU를 **동시에** 쓰도록 NVIDIA가 중재. 메모리 격리는 약하다 | 한 MRI를 **여러 기사가 동시에** 조작 (조율자 있음) |

## 핵심 개념
- **GPU 메모리 = 가중치 + KV 캐시 + 여유분.** 가중치는 "파라미터 수 × 파라미터당 바이트"다. 7B를 FP16으로 올리면 7 × 2 = 14GB, INT4면 3.5GB다. 여기에 동시 사용자 × 컨텍스트 길이만큼 KV 캐시가 더 붙는다. 그래서 "모델이 들어간다"와 "100명이 동시에 쓸 수 있다"는 전혀 다른 질문이다.
- **양자화 트레이드오프**: FP16 → INT8 → INT4로 갈수록 메모리와 비용은 줄고 속도는 대체로 빨라지지만 정확도가 조금씩 떨어진다. 한국어나 전문 용어처럼 섬세한 작업은 INT4에서 품질 저하가 더 잘 보인다. 실무에서는 같은 질문 세트로 품질을 비교해서 정한다.
- **sLLM을 쓰는 이유**: 사내 문서 검색(RAG)처럼 "근거 문서를 주고 요약·정리하게 하는" 작업은 큰 모델이 아니어도 잘한다. 폐쇄망과 데이터 반출 금지 환경에서는 외부 API를 쓸 수 없고, GPU 비용도 모델 크기에 비례한다.
- 비유: 큰 LLM은 **모든 과를 아는 대학병원 교수**, sLLM은 **특정 분야 매뉴얼을 옆에 둔 동네 의원 원장님**이다. 매뉴얼(RAG 문서)만 잘 주면 원장님도 충분히 정확하게 답한다.

## 이 프로젝트에서 내가 한 것
- `charts/ai-platform` Helm 차트를 만들었다. `llm-serving`(Ollama 0.40.0 + qwen2.5:3b)과 `embedding-serving`(Ollama + bge-m3)을 각각 Deployment + PVC + Service로 구성했다.
- 둘 다 `nodeSelector: node-role=gpu` + toleration으로 GPU 노드에 배치하고 `nvidia.com/gpu: 1`씩 요청한다. 가짜 GPU 2개를 둘이 다 쓰는 구조라, M8의 "GPU 3개 요청 → Pending" 시나리오로 이어진다.
- 메모리 requests/limits를 계산 근거와 함께 values.yaml 주석에 적었다.
  - LLM: 가중치 약 1.9GB + KV 캐시(36KB/토큰 × 4096 × 4슬롯 ≈ 0.6GB) + 여유 0.5GB ≈ 3GB → requests 3Gi, limits 4Gi
  - 임베딩: 568M × 2바이트 ≈ 1.2GB + 여유 → requests 1.5Gi, limits 2.5Gi
- **probe 3종을 역할별로 나눴다.** startup은 서버가 뜰 때까지 기다리고, readiness는 `ollama show 모델명`으로 **모델이 PVC에 있을 때만 Ready**로 둔다. liveness는 서버 응답이 없을 때 재시작한다. 모델이 없는데 트래픽을 받으면 사용자가 오류를 보기 때문에 readiness에 모델 검사를 넣었다.
- `scripts/preload-models.sh`: curl Job이 각 서빙 Pod에 `/api/pull`을 요청해서 모델을 PVC에 저장한다. Pod가 재시작돼도 다시 받지 않는다. M5 폐쇄망 리허설에서는 이 단계를 반입 파일 복사로 바꾼다.
- REAL GPU 노드용으로 `engine: vllm` 옵션도 차트에 넣었다. 렌더링까지만 확인했고, 이 PC에서 동작은 검증하지 않았다.
- `scripts/bench-llm.py`(표준 라이브러리만 사용, OpenAI 호환 API): 동시 요청 1/4/8개의 TTFT 평균·p95, 요청당 토큰/초, 총 처리량을 측정한다.
- **벤치마크 결과** (2026-10-07, CPU 추론, Ryzen 5 5600, qwen2.5:3b Q4_K_M, num_parallel=4, max_tokens=128, temperature 0):

  | 동시 요청 | 성공 | TTFT 평균(s) | TTFT p95(s) | 토큰/초(요청당) | 전체 시간 평균(s) | 총 처리량(토큰/s) |
  |---|---|---|---|---|---|---|
  | 1 | 1/1 | 0.12 | 0.12 | 15.9 | 8.18 | 15.7 |
  | 4 | 4/4 | 2.51 | 2.52 | 10.5 | 14.70 | 34.8 |
  | 8 | 8/8 | 6.59 | **13.00** | 9.2 | 20.57 | 36.3 |

  **해석**
  - 동시 요청이 1 → 4가 되자 요청당 속도는 15.9 → 10.5로 줄었지만, **서버 전체 처리량은 15.7 → 34.8로 2.2배**가 됐다. 여러 요청을 한 번에 계산하는 배치 효과다.
  - 4 → 8에서는 처리량이 34.8 → 36.3으로 거의 그대로이고, **TTFT p95가 13초로 폭증**했다. 슬롯이 4개(`num_parallel=4`)라 5~8번째 요청은 앞 요청이 끝날 때까지 **대기열에서 기다렸기** 때문이다. CPU가 포화된 지점이다.
  - 결론: 이 구성의 적정 동시성은 4이고, 그 이상은 늘려도 처리량은 안 늘고 대기 시간만 늘어난다. 사용자가 더 많으면 레플리카(서버 대수)를 늘리거나 GPU가 필요하다. M6에서 "TTFT p95 > 5초" 알람, M8 시나리오 6(latency-spike)과 연결된다.
  - 주의: 동시 1개의 TTFT 0.12초는 워밍업과 같은 프롬프트라 **프롬프트 캐시**가 재사용된 영향이 있다. 실제 첫 요청(모델 로딩 포함 콜드 스타트)은 **38.8초**였다. 그래서 `OLLAMA_KEEP_ALIVE=-1`로 모델을 메모리에 계속 올려 둔다.
  - 메모리: GPU 노드 컨테이너는 LLM과 임베딩을 합쳐 약 5.6GB를 썼다(`docker stats`).
- **품질 관찰**: RAG 없이 "유압 압력 저하 원인"을 물었더니 "플와이어 시스템 중단" 같은 **없는 용어를 지어냈다(환각)**. 3B 모델은 근거 문서 없이는 믿을 수 없다는 걸 실측으로 확인했고, M4에서 근거 문서를 붙이고 "근거 없으면 모른다고 답하기"를 넣는 이유가 됐다.
- 임베딩 확인: bge-m3로 3문장을 임베딩해 보니 1024차원이었다. 코사인 유사도는 "E-203 유압 압력 저하" ↔ "유압이 떨어졌을 때 조치" 0.570, ↔ "점심 메뉴 추천" 0.254로, 뜻이 가까운 문장이 더 가깝게 나왔다.
- **겪은 문제 2가지**:
  1. **교착 상태**: preload Job이 10분 넘게 "서버 대기..."만 찍었다. 모델 폴더 크기(16K 그대로)와 서버 로그(`/api/pull` 요청 없음), `kubectl get endpointslices`(ready=false)를 차례로 확인해서 원인을 찾았다. **Service는 Ready Pod에만 연결되는데, Pod는 모델이 있어야 Ready**라서 서로 기다리고 있었다. 사용자용 Service는 그대로 두고, `publishNotReadyAddresses: true`인 관리용 `-admin` Service를 따로 만들어 해결했다.
  2. **progress deadline 초과**: 위 문제로 Pod가 17분간 NotReady라 Deployment 기본 진행 기한(600초)을 넘었다. 복구 후 상태는 정상(`NewReplicaSetAvailable`)으로 돌아왔지만, 큰 모델은 첫 적재가 10분을 넘을 수 있어서 `progressDeadlineSeconds: 1800`을 명시했다.

## 실제 기업 환경에서는
- **GPU 서버에서는 vLLM이나 TensorRT-LLM, Triton을 주로 쓴다.** vLLM은 PagedAttention으로 KV 캐시를 페이지 단위로 관리하고, continuous batching으로 요청을 계속 끼워 넣어서 동시 처리량이 Ollama보다 훨씬 높다. Ollama는 개발과 소규모 용도에 적합하다.
- 70B급 모델은 GPU 한 장(80GB)에 안 들어가서 **텐서 병렬(TP)**로 여러 GPU에 나눠 올린다. 같은 서버 안의 GPU끼리는 NVLink로 빠르게 통신한다.
- **GPU 공유**: 작은 모델 여러 개를 운영하면 H100 한 장을 통째로 주는 건 낭비라서 MIG로 쪼갠다. 격리가 필요 없는 개발 환경은 time-slicing을 쓴다. GPU Operator 설정으로 켠다.
- 폐쇄망 고객은 모델 파일(수~수백 GB)을 해시값과 함께 반입한다. 내부 오브젝트 스토리지(MinIO)나 모델 레지스트리에 올리고, 서빙 Pod는 거기서 받는다.
- 운영 지표는 TTFT p95, 토큰/초, 대기열 길이, GPU 사용률과 메모리, 그리고 동시 사용자당 비용이다. SLA는 보통 "TTFT p95 3초 이내"처럼 정한다.

## 예상 면접 질문 5개 + 모범 답변

**Q1. 7B 모델을 서빙하려면 GPU 메모리가 얼마나 필요한가요?**
> 가중치는 파라미터 수 곱하기 파라미터당 바이트라서, FP16이면 7B × 2바이트로 약 14GB, INT4로 양자화하면 3.5GB 정도입니다. 그런데 이건 모델만 올린 거고, 실제로는 동시 사용자 수 × 컨텍스트 길이만큼 KV 캐시가 더 들고 런타임 여유분도 필요합니다. 그래서 FP16 7B를 여러 명이 쓰려면 24GB 카드는 빠듯하고 40~48GB급을 보는 게 안전하다고 생각합니다. 저는 이 공식으로 제 PC용 3B 모델 메모리를 계산해서 쿠버네티스 requests/limits에 근거와 함께 적어 두었습니다.

**Q2. TTFT와 토큰/초는 각각 무엇이고 왜 따로 봐야 하나요?**
> TTFT는 질문을 보내고 첫 글자가 나오기까지 시간이고, 토큰/초는 그 뒤에 답이 써지는 속도입니다. TTFT는 입력 길이와 대기열에 영향을 많이 받아서, RAG처럼 참고 문서를 길게 넣거나 동시 사용자가 몰리면 확 늘어납니다. 토큰/초는 모델 크기와 GPU 메모리 대역폭에 좌우되고요. 사용자 체감은 TTFT가 크게 좌우해서 알람도 TTFT p95로 거는 게 맞다고 봤고, 동시 요청 1, 4, 8개에서 둘 다 측정해 봤습니다.

**Q3. 양자화를 하면 무엇을 얻고 무엇을 잃나요?**
> 메모리가 줄어서 같은 GPU에 더 큰 모델을 올리거나 동시 사용자를 늘릴 수 있고, 메모리 대역폭 부담이 줄어서 대체로 생성 속도도 빨라집니다. 대신 정확도가 조금 떨어지는데, 4비트까지 내리면 한국어나 전문 용어에서 차이가 보일 수 있다고 알고 있습니다. 그래서 실무에서는 고객 업무 질문 세트로 FP16과 INT8, INT4 답변 품질을 비교해 보고 결정해야 한다고 생각합니다. 저는 이번에 메모리 제약 때문에 4비트를 썼고, 품질 비교까지는 아직 못 해 봤습니다.

**Q4. Ollama, vLLM, Triton은 어떻게 다르고 언제 무엇을 쓰나요?**
> Ollama는 설치가 쉽고 CPU에서도 돌아서 개발이나 소규모 용도에 좋습니다. vLLM은 PagedAttention과 continuous batching 덕분에 GPU에서 동시 요청이 많을 때 처리량이 훨씬 높아서 운영용 LLM 서빙에 많이 씁니다. Triton은 NVIDIA의 범용 추론 서버라서 LLM뿐 아니라 비전 모델 같은 여러 모델을 한 서버에서 같이 운영할 때 씁니다. 제 PC는 GPU를 쿠버네티스에 붙이지 못해서 Ollama로 했고, 차트에는 GPU 환경에서 vLLM으로 바꿀 수 있는 옵션을 넣어 뒀는데 그건 실제로 돌려 보진 못했습니다.

**Q5. 쿠버네티스에서 GPU는 왜 limits로만 요청하고, 여러 Pod가 GPU 하나를 나눠 쓰려면 어떻게 하나요?**
> GPU 같은 확장 리소스는 오버커밋이 안 되고 정수로 통째로 할당돼서, limits만 쓰면 requests도 같은 값으로 잡힙니다. 그래서 기본적으로는 Pod 하나가 GPU 한 장을 독점합니다. 나눠 쓰려면 세 가지 방법이 있는데요, A100·H100에서는 MIG로 GPU를 물리적으로 최대 7개로 쪼갤 수 있고, time-slicing은 시간을 나눠 번갈아 쓰는 방식이라 격리가 약하고, MPS는 여러 프로세스가 동시에 쓰게 해 줍니다. 운영 환경에서 격리가 중요하면 MIG, 개발 환경이면 time-slicing을 고려하겠습니다.

**보너스 Q. 배포했는데 Pod가 계속 NotReady입니다. 어떻게 접근하셨나요?** (실제 겪은 문제)
> 실제로 겪었는데요, 모델을 받는 Job이 10분 넘게 "서버 대기"만 하고 있었습니다. 바로 고치지 않고 먼저 모델 폴더 크기를 봤더니 16KB 그대로라서 다운로드가 시작도 안 된 걸 알았고, 서버 로그에도 다운로드 요청이 없었습니다. 그래서 Service 엔드포인트를 보니 ready가 false였습니다. Service는 Ready Pod에만 트래픽을 보내는데, 제가 readiness를 "모델이 있어야 통과"로 만들어서 모델을 넣으려는 요청이 못 들어가는 교착 상태였던 거죠. 사용자용 Service는 그대로 두고, NotReady Pod에도 연결되는 관리용 Service를 따로 만들어서 해결했습니다.

## 꼬리 질문 3개 + 답변 방향
1. **"KV 캐시는 어떻게 계산했어요?"** → 토큰당 2(K, V) × 레이어 수 × KV 헤드 수 × 헤드 차원 × 바이트. qwen2.5:3b는 36레이어, KV 헤드 2개(GQA), 헤드 차원 128, FP16이라 토큰당 약 36KB다. 4096 컨텍스트 × 4슬롯이면 약 0.6GB. GQA가 KV 헤드를 줄여서 KV 캐시를 크게 아껴 준다.
2. **"readiness와 liveness를 왜 다르게 했어요?"** → 모델이 없을 때 liveness가 실패하면 Pod가 계속 재시작만 하고 다운로드는 영원히 못 끝난다. "트래픽을 받을 수 있나"(readiness)와 "프로세스가 살아 있나"(liveness)는 다른 질문이다. 그리고 모델 로딩처럼 느린 시작은 startupProbe로 보호한다.
3. **"임베딩 모델을 바꾸면 무슨 일이 생겨요?"** → 차원이 다르면(예: 1024 → 768) pgvector 컬럼과 안 맞아서 오류가 나고, 차원이 같아도 좌표계가 달라서 검색 결과가 엉망이 된다. 모델을 바꾸면 전체 문서를 다시 임베딩해야 한다. M8 시나리오 5번에서 재현한다.
