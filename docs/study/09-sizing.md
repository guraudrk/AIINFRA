# 09. 사이징과 기술 제안 — 요구사항을 GPU 대수로 바꾸기

## 한 줄 요약
가중치 + KV 캐시 + 여유분 공식을 계산기(`/sizing`, pytest 12개)로 만들고, 가상 RFP(800명, 동시 100명, 문서 2만 건, 폐쇄망)를 정량화해 **32B FP8 · 동시 30건 = 70.6GB → L40S 2장 1벌, 4장 서버 2대 이중화**를 제안했다. 핵심 발견은 **KV 캐시가 가중치만큼 크다**는 것이다.

## 용어 풀이 (비전공자용)
> 비유 기준: 클러스터 = 병원. 이번에는 **새 병원을 지으려는 고객에게 병상·장비 규모를 계산해 설계 제안서를 쓰는 일**이다.

| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **사이징** | 요구사항(사용자 수, 데이터 양)을 장비 규모(GPU 수, 메모리, 저장 용량)로 바꾸는 계산 | 환자 수로 **병상·MRI 대수** 정하기 |
| **RFP** | 고객이 "이런 시스템을 원한다"고 업체에 보내는 제안 요청서 | 병원 신축 **입찰 공고** |
| **PoC** | 본 구축 전에 작게 시험해서 되는지 확인하는 검증 단계. 성공 기준을 숫자로 정한다 | **시범 진료소** 운영 |
| **동시 사용자 vs 동시 요청** | 화면을 열어 둔 사람 수 vs 같은 순간 답을 만들고 있는 요청 수. 보통 후자가 훨씬 적다 | 대기실 인원 vs **진료 중인 환자 수** |
| **텐서 병렬 (TP)** | 모델 하나를 여러 GPU에 쪼개 올려 함께 계산. GPU 간 통신이 많아 같은 서버 안(NVLink·PCIe)에서 한다 | 큰 수술을 **의사 둘이 나눠** 집도 |
| **레플리카** | 같은 모델을 여러 벌 띄워 요청을 나누고, 하나가 죽어도 서비스 유지 | 같은 진료실을 **두 개** 운영 |
| **학습 vs 추론** | 학습은 모델을 만드는 것(GPU 대량·고속 통신), 추론은 만든 모델로 답하는 것(메모리·지연 중심) | 의대 교육 vs **진료** |
| **GPU 세대** | Ampere(A100) → Hopper(H100·H200) → Blackwell. 새 세대일수록 FP8 같은 저정밀 연산과 메모리 대역폭이 좋아진다 | MRI 장비 **세대** |
| **CAPEX / OPEX** | 장비를 사는 초기 투자 / 쓰는 만큼 내는 운영 비용 | 장비 **구매** vs **임대** |
| **TCO** | 구매·전력·공간·운영 인력까지 합친 총소유비용 | 장비 값 + 유지비 + 인건비 |

## 핵심 개념
- **LLM GPU 메모리 = 가중치 + KV 캐시 + 여유분**
  - 가중치 = 파라미터 × 바이트 (7B FP16 = 14GB, FP8 = 7GB, INT4 = 3.5GB)
  - KV 캐시 = 2 × 레이어 × KV헤드 × 헤드차원 × 2바이트 × 컨텍스트 × **동시 요청**
  - 여유 = 10% (활성값, CUDA 컨텍스트, 단편화), GPU는 90%만 쓴다고 본다
- **GPU 대수는 모델 크기보다 동시성과 컨텍스트가 결정한다.** 32B FP8은 가중치 32GB인데, 동시 30건 × 4K 컨텍스트면 KV 캐시도 32GB다. 동시 요청이 2배면 KV도 2배다.
- **요구사항 정량화가 사이징의 절반이다.** "100명이 쓴다"를 "동시 생성 요청 30건, 요청당 4K 토큰"으로 바꾸는 가정(활성 비율)을 명시하고, PoC 로그로 보정한다.
- **숫자는 근사치, 판단 기준을 함께 제시한다.** 고객은 숫자 하나보다 "왜 이 구성인지(이중화, 확장 여유, 폐쇄망)"를 산다.
- 비유: 병원 설계에서 **의사 수(모델)**보다 **동시에 진료받는 환자 수(동시 요청)와 진료 시간(컨텍스트)**이 진료실 수(GPU)를 정한다.

## 이 프로젝트에서 내가 한 것
- **계산기** `apps/sizing` (FastAPI + 단순 HTML, `https://localhost/sizing`)
  - LLM: 파라미터·정밀도·동시 사용자·활성 비율·컨텍스트 → 가중치·KV·여유 → **GPU별(L40S 48 / A100 80 / H100 80 / H200 141GB) 텐서 병렬 장수**. A100에서 FP8을 고르면 경고, PCIe 텐서 병렬이면 통신 병목 주의를 표시한다.
  - 벡터DB: 문서 수·쪽수 → 청크 수 → 벡터 + HNSW 링크 + 본문 용량, 최초 임베딩 시간(M3 CPU 실측 2.2청크/초 외삽)
  - 운영: 일 질의 → 감사 로그 연 용량, 백업 용량(일 1회 × 7개 × 압축)
  - "근사치" 문구가 들어간 **Markdown 제안서 다운로드**
  - 계산식 검증 **pytest 12개**: 7B FP16 = 14GB, M2의 KV 캐시 0.6GB 재현, 70B FP16은 H100 1장에 불가 등. Docker 빌드 단계에서 테스트를 돌려 **실패하면 이미지가 안 만들어지게** 했다. 실제로 반올림을 고려하지 않은 테스트 기대값 1건을 빌드가 잡아냈다.
- **가상 RFP 제안서** `docs/proposal-sample.md`
  - 정량화: 동시 100명 × 30% = 동시 요청 30건, 4K 컨텍스트, 32B FP8(3B의 환각 실측을 근거로 상위 모델), 문서 2만 건 → 청크 50만 개
  - 사이징: **70.6GB** (가중치 32.0 + KV 32.2 + 여유 6.4) → L40S 2장(TP2) 1벌 / H100 1장은 70.6/72GB로 여유 없음
  - 제안: **L40S 4장 서버 2대** — 서버당 LLM 1벌로 이중화, 남는 GPU로 임베딩·에이전트·비전 AI 단계 시작. 벡터DB 5.3GB는 pgvector로 충분, HNSW 상주를 위해 DB 메모리 확보
  - 단계별 일정(13주 + 확장), **PoC 성공 기준 수치**(근거 적중 80%, 권한 노출 0건, TTFT p95 3초, 폐쇄망 1일 재구축, RTO 1시간), 운영 3명 기준 1·2·3차 지원 체계, 리스크 7개

## 실제 기업 환경에서는
- **요구사항 정량화 질문 리스트** (고객 미팅에서 묻는 것)
  1. 총 사용자 / 동시 접속 / 피크 시간대(교대·조회 몰리는 시간)는?
  2. 주 사용 시나리오: 짧은 Q&A인가, 긴 문서 요약인가? (컨텍스트 길이)
  3. 응답 속도 기대치: 첫 글자 몇 초 이내? (TTFT 목표)
  4. 문서: 건수·형식(PDF·HWP·스캔본)·갱신 주기·권한 체계(원천 시스템)?
  5. 보안: 폐쇄망 여부, 반입 절차, 감사 로그 보관 기간, 개인정보 포함 여부?
  6. 가용성: 업무 시간만인가 24시간인가, 허용 중단 시간(RTO)·데이터 손실(RPO)?
  7. 확장 계획: 에이전트·비전·학습(파인튜닝) 계획과 시기?
  8. 운영 인력·역량, 기존 인프라(가상화, 스토리지, 백업 솔루션, 모니터링)?
  9. 상면·전력·냉각 여유 (GPU 서버는 대당 수 kW)?
- **GPU 선택 감각**: 7~14B 추론은 L40S 1장으로 충분한 경우가 많다. 30B급은 L40S 2장이나 H100 1장, 70B급은 H100·H200 여러 장의 텐서 병렬이 필요하다. 긴 컨텍스트·많은 동시 사용자는 HBM 큰 H200이 유리하다. **학습(파인튜닝)**은 메모리(옵티마이저 상태 포함, 가중치의 수 배)와 GPU 간 고속 통신(NVLink, InfiniBand)이 핵심이라 추론과 사이징이 완전히 다르다.
- 실제 제안에서는 **벤치마크 데이터**(vLLM 처리량, 고객 질문 세트 품질)와 **TCO**(전력·냉각·상면 포함)를 함께 제시하고, 벤더(Dell 등) 레퍼런스 구성을 활용한다.
- **비전공 고객에게 설명하는 법**: 기술 용어 대신 영향으로 말한다. "GPU 2장이 모델 1벌을 담당하고, 서버 2대에 1벌씩 두어 한 대가 고장 나도 쓸 수 있습니다", "동시에 질문하는 사람이 두 배가 되면 GPU 메모리도 거의 두 배가 필요합니다". 숫자는 근사치라고 먼저 말하고, PoC로 확인하겠다고 약속한다.

## 예상 면접 질문 5개 + 모범 답변

**Q1. 고객이 "직원 800명이 쓸 AI를 만들고 싶은데 GPU가 몇 장 필요하냐"고 묻는다면?**
> 바로 숫자를 드리기보다 먼저 몇 가지를 여쭙겠습니다. 동시에 쓰는 사람이 몇 명인지, 주로 짧은 질문인지 긴 문서 요약인지, 응답 속도를 어느 정도 기대하시는지, 폐쇄망인지요. 그걸로 동시 생성 요청 수와 컨텍스트 길이를 정하고, 가중치 더하기 KV 캐시 더하기 여유분으로 메모리를 계산합니다. 가상 RFP로 해 보면 동시 100명을 동시 요청 30건으로 보고 32B 모델을 FP8로 올리면 약 71GB라 L40S 2장에 1벌이 들어가서, 이중화를 위해 4장짜리 서버 2대를 제안했습니다. 다만 이건 근사치라 PoC에서 실제 질문으로 측정해 확정하겠다고 말씀드리겠습니다.

**Q2. KV 캐시가 왜 중요한가요?**
> KV 캐시는 모델이 앞에서 읽은 내용을 다시 계산하지 않으려고 저장해 두는 메모리인데, 컨텍스트 길이와 동시 요청 수에 비례해서 커집니다. 계산해 보니 32B FP8 모델에서 가중치가 32GB인데 동시 30건, 4천 토큰이면 KV 캐시도 32GB였습니다. 즉 모델이 GPU에 들어간다고 끝이 아니고, 사용자가 늘면 KV 캐시 때문에 GPU가 모자라게 됩니다. 그래서 RAG처럼 근거 문서를 길게 넣는 서비스는 컨텍스트 관리와 동시성 설계가 GPU 비용을 좌우한다고 봅니다.

**Q3. L40S, H100, H200은 어떻게 고르나요?**
> 추론 위주에 7~14B 모델이면 L40S로도 충분한 경우가 많고, PCIe라 서버 구성이 유연합니다. 30B급 이상이나 텐서 병렬이 필요하면 NVLink가 있는 H100이 유리하고, 긴 컨텍스트나 동시 사용자가 많아 KV 캐시가 크면 메모리가 141GB인 H200이 좋습니다. A100은 FP8을 지원하지 않아서 FP8 양자화 모델을 쓰려면 고려해야 합니다. 학습까지 한다면 GPU 간 고속 통신이 핵심이라 기준이 완전히 달라집니다. 제 계산기에서도 GPU별로 필요한 장수와 이런 주의점을 같이 표시하게 했습니다.

**Q4. 온프레미스와 클라우드 LLM API 중 무엇을 권하시겠어요?**
> 고객 조건에 따라 다릅니다. 폐쇄망이 필수거나 문서를 외부로 보낼 수 없으면 온프레미스가 사실상 유일한 선택지입니다. 비용은 초기 투자가 크지만 사용량이 많을수록 유리하고, 클라우드 API는 초기 부담이 적은 대신 사용량에 비례해 늘어납니다. 운영 인력이 적으면 클라우드가 편하지만, 온프레미스도 자동 감시와 런북, 기술지원 계약으로 보완할 수 있습니다. 이번 가상 RFP는 폐쇄망 조건이라 온프레미스로 제안했습니다.

**Q5. PoC는 어떻게 설계하나요?**
> 성공 기준을 숫자로 먼저 고객과 합의합니다. 예를 들어 현업과 만든 질문 100개에서 근거 문서 적중 80% 이상, 권한 밖 문서 노출 0건, 동시 30건에서 첫 응답 p95 3초 이내, 폐쇄망 재구축 하루 이내, 복구 1시간 이내 같은 식입니다. 그리고 모델 크기나 양자화를 바꿔 가며 같은 질문 세트로 비교해서 품질, 속도, GPU 수의 트레이드오프를 표로 보여 드리고 결정하시게 합니다. 제 프로젝트에서도 권한 테스트, 폐쇄망 리허설, 복구 훈련을 수치로 남겼는데, PoC 성공 기준을 그 방식으로 만들었습니다.

## 꼬리 질문 3개 + 답변 방향
1. **"활성 비율 30%는 어디서 나왔나요?"** → 가정이다. 화면을 연 사람이 모두 같은 순간 생성 중이지는 않다는 경험칙을 썼고, PoC나 기존 시스템 로그(피크 시간대 동시 요청)로 보정해야 한다고 명시했다. 피크가 크면 대기열 알람과 여유 GPU로 대응한다.
2. **"양자화하면 품질이 떨어지지 않나요?"** → 떨어질 수 있다. FP8은 손실이 작고 INT4는 한국어·전문 용어에서 차이가 보일 수 있다. 그래서 PoC에서 FP16·FP8·INT4를 같은 질문 세트로 비교해 결정한다.
3. **"전력과 냉각은 고려했나요?"** → 계산기에는 넣지 않았다. GPU 서버는 대당 수 kW라 랙당 전력·냉각 한도가 실제 제약이 된다. 고객 현장 상면·전력 확인을 요구사항 질문 리스트에 넣었다.
