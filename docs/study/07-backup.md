# 07. 백업과 복구 훈련 — "복구해 봐야 백업이다"

## 한 줄 요약
pg_dump 백업을 MinIO에 매일 쌓고(7개 보관, 실패 시 알람), 문서·청크 테이블을 실제로 지운 뒤 최신 백업으로 복구하는 훈련을 해서 **RTO 48초, RPO 36초**를 실측했다. 백업 이후 데이터는 실제로 사라지는 것까지 확인했다.

## 용어 풀이 (비전공자용)
> 비유 기준: 클러스터 = 병원. 이번에는 **진료 기록 사본을 금고에 보관하고, 원본이 불타도 사본으로 되살리는 훈련**을 했다.

| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **백업** | 특정 시점의 데이터를 따로 복사해 두는 것. 실수로 지우거나 랜섬웨어에 감염돼도 그 시점으로 되돌릴 수 있다 | 진료 기록 **사본을 금고에 보관** |
| **복제 (Replication)** | 데이터를 실시간으로 다른 서버에 똑같이 쓰는 것. 서버 고장에는 강하지만, **실수로 지운 것도 그대로 복제**된다 | 원본과 **동시에 쓰는 먹지** — 원본에 낙서하면 먹지에도 낙서 |
| **RAID** | 디스크 여러 개를 묶어 디스크 하나가 고장 나도 데이터를 지키는 기술. 백업이 아니다 | 같은 장부를 **두 권 동시에 기록** |
| **RPO** (Recovery Point Objective) | 장애가 나면 **최대 얼마 전 시점까지의 데이터를 잃어도 되는가**. 백업 주기가 결정한다 | 사본을 **몇 시간마다** 뜨는가 |
| **RTO** (Recovery Time Objective) | 장애가 나면 **얼마 만에 서비스를 되살려야 하는가** | 화재 후 **진료 재개까지 걸리는 시간** |
| **3-2-1 원칙** | 사본 **3개**, 서로 다른 매체 **2종**, 그중 **1개는 다른 장소(오프사이트)** | 금고 2개 + **다른 건물 금고 1개** |
| **불변 백업 (Immutable)** | 정해진 기간 동안 **아무도(관리자도) 지우거나 고칠 수 없게** 잠근 백업. 랜섬웨어가 백업까지 지우는 것을 막는다 | **시한 잠금 금고** |
| **pg_dump / pg_restore** | PostgreSQL의 논리 백업·복구 도구. 테이블 정의, 데이터, 인덱스, 권한, RLS 정책까지 파일 하나로 뽑고 되살린다 | 기록을 **양식째 복사**·되붙이기 |
| **논리 백업 vs 물리 백업** | 논리: SQL 수준으로 내보냄(이식성 좋음, 큰 DB는 느림). 물리: 데이터 파일 자체를 복사(빠름, 같은 버전 필요) | 내용을 **옮겨 적기** vs 장부를 **통째로 복사** |
| **WAL / PITR** | WAL은 DB의 모든 변경 기록(작업 일지). 이걸 계속 보관하면 원하는 **특정 시각으로 되돌리는 복구(PITR)**가 가능해 RPO가 초 단위로 준다 | 사본 + **그 이후의 모든 작업 일지** |
| **단일 트랜잭션 복구** | 복구 도중 실패하면 전부 취소해서, 반쯤 복구된 어정쩡한 상태가 남지 않게 한다 | 장부 교체는 **전부 아니면 전무** |
| **보관 정책 (Retention)** | 백업을 몇 개·며칠치 남길지. 무한히 쌓으면 저장소가 찬다 | 사본은 **최근 7개만** |
| **Velero** | 쿠버네티스 리소스와 볼륨을 오브젝트 스토리지로 백업·복구하는 도구 | 병원 **시설 전체 설계도 + 장비 사진** 백업 |

## 핵심 개념
- **복제·RAID는 백업이 아니다.** 하드웨어 고장에는 강하지만, 사람의 실수(DROP TABLE)와 랜섬웨어 암호화도 그대로 복제된다. 시점을 되돌릴 수 있는 별도 사본이 있어야 백업이다.
- **RPO는 백업 주기가, RTO는 복구 절차와 데이터 크기가 결정한다.** 일 1회 백업이면 최악의 RPO는 24시간이다. 그보다 짧아야 하면 WAL 아카이빙(PITR)이나 복제를 더한다. RTO는 "얼마나 빨리 받아서, 되살리고, 확인하는가"라서 **실제로 해 봐야만 안다.**
- **백업은 복구 테스트까지가 백업이다.** 파일이 쌓이고 있다는 것과 그 파일로 되살아난다는 것은 다르다. 권한, 확장 기능(pgvector), RLS 정책, 인덱스까지 같이 돌아와야 서비스가 정상이다.
- 비유: 진료 기록 **사본을 매일 금고(MinIO)에 넣고**, 최근 7부만 남긴다. 금고가 하루 넘게 안 채워지면 **경보**가 울린다. 그리고 실제로 **원본을 태워 보고**(테이블 삭제) 사본으로 진료를 재개하기까지 몇 초 걸리는지(RTO), 마지막 사본 이후 기록은 얼마나 잃는지(RPO)를 재 봤다.

## 이 프로젝트에서 내가 한 것
- **DB 백업 CronJob `pg-backup`** (매일 02:00, Helm 차트)
  - initContainer(PostgreSQL 이미지): `pg_dump -Fc`(압축 커스텀 포맷) → emptyDir. **슈퍼유저로** 덤프한다. RLS가 걸린 테이블을 일반 계정으로 덤프하면 일부 행만 나오거나 오류가 나기 때문이다.
  - 업로드 컨테이너(수집 이미지의 boto3 재사용): MinIO `backups/postgres/hanbit-<UTC시각>.dump` 업로드 + **최근 7개만 보관**(이름이 시각순이라 정렬 후 오래된 것 삭제)
  - NetworkPolicy: 백업·복구 Job은 DB(5432)와 MinIO(9000)로만 나간다.
  - 감시: M6의 `BackupNotSucceeded24h` 알람이 kube-state-metrics의 CronJob 마지막 성공 시각을 본다. 백업 직후 "마지막 성공 후 82초"로 잡히는 것을 확인했다.
  - 실측: 덤프 **507KB**(문서 18개, 청크 138개, 정비 이력 200건), 백업 Job **11초**
- **쿠버네티스 설정 백업**: Velero 대신 `scripts/k8s-export.sh`로 Helm 릴리스 값·렌더링 매니페스트와 객체 목록을 tar로 묶는다(68KB). 이유는 세 가지다. ① 설정 원본은 git에 있다(차트·values·vendor). ② 잃으면 안 되는 상태는 DB·MinIO 데이터다. ③ Velero로 kind의 PV 데이터까지 백업하려면 node-agent 같은 추가 구성이 크다. **Secret 값은 내보내지 않는다**(이름·키 목록만). 평문 유출 위험 때문이다.
- **복구** `scripts/restore.sh`: MinIO에서 최신(또는 지정) 덤프를 받아 `pg_restore --clean --if-exists --single-transaction`. 실패하면 전부 롤백된다.
- **복구 훈련** `scripts/restore-drill.sh` → `docs/restore-drill-report.md`
  | 시각 | 내용 |
  |---|---|
  | 16:53:34 | 사전: 문서 18, 청크 138, 서비스 정상 |
  | 16:53:50 | 백업 완료 (507,228 bytes) |
  | 16:54:10 | 백업 이후 감사 로그 표식 1건 추가 → **장애: DROP TABLE chunks, documents** |
  | 16:54:19 | 실제 질문 → **HTTP 503** (서비스 중단 확인) |
  | 16:54:33 | 복구 완료 |
  | 16:54:58 | 문서 18 / 청크 138, RLS 정책 4개 복구, 질문 정상. **표식 0건 = 백업 이후 데이터는 잃음** |
  - **RTO 48초, RPO 36초**

## 실제 기업 환경에서는
- **3-2-1 + 불변 백업**: 운영 DB → 로컬 백업 장비 → 오프사이트(다른 센터·클라우드) 사본. 랜섬웨어가 백업 서버 관리자 계정까지 탈취하는 경우가 많아서, **불변(Immutable) 저장소**에 보관한다. MinIO의 Object Lock(WORM), 엑사그리드의 랜섬웨어 복구 계층(retention time-lock), Veeam의 Hardened Repository가 그 역할이다.
- **DB는 논리 + 물리 + WAL**: 큰 DB는 pg_dump가 느려서 물리 백업(pgBackRest, Barman) + **WAL 아카이빙으로 PITR**을 한다. EDB·CloudNativePG 오퍼레이터는 이를 S3(MinIO)로 자동화한다. RPO 수 분, RTO는 데이터 크기에 비례.
- **쿠버네티스**: Velero(또는 Kasten K10, Veeam의 쿠버네티스 백업)로 네임스페이스 리소스 + PV 스냅샷(CSI)을 함께 백업한다. 설정은 GitOps(Argo CD)로 git에서 재현한다.
- **AI 플랫폼 특유의 백업 대상**: 벡터DB(재임베딩하면 다시 만들 수 있지만 수 시간~수 일 걸려 RTO에 불리 → 백업 대상), 원본 문서(최우선), 모델 파일(재반입 가능하지만 폐쇄망이면 반입 절차가 길어 보관 권장), 감사 로그(규정상 보존 의무, RPO 최소화).
- 복구 훈련은 **정기적으로**(분기 등) 하고, 결과(RTO/RPO)를 고객 SLA와 비교해 보고한다.

## 에티버스그룹 사업과의 연결
에티버스는 **Veeam, 엑사그리드, MinIO** 총판이다. 이번 구성(DB 덤프 → S3 호환 오브젝트 스토리지, 보관 정책, 성공 감시, 복구 훈련)은 그 제품들이 엔터프라이즈 규모로 해 주는 일을 작게 재현한 것이다. 고객에게 백업 솔루션을 제안할 때 "백업이 되나요?"가 아니라 **"우리 데이터 규모에서 RTO/RPO가 얼마인가, 랜섬웨어에도 안전한가"**로 답해야 한다는 걸 체감했다.

## 자주 쓰는 명령어
```bash
make backup                                  # 즉시 DB 백업 + k8s 설정 내보내기
make restore                                 # 최신 백업으로 복구
BACKUP_KEY=postgres/hanbit-...dump ./scripts/restore.sh   # 특정 시점 백업으로 복구
CONFIRM=yes ./scripts/restore-drill.sh       # 복구 훈련 (테이블 실제 삭제)
kubectl -n ai-platform get cronjob pg-backup # LAST SCHEDULE, 마지막 성공
./scripts/prom-query.sh 'time() - kube_cronjob_status_last_successful_time{cronjob="pg-backup"}'
# PostgreSQL
pg_dump -Fc -d hanbit -f hanbit.dump         # 압축 커스텀 포맷
pg_restore -l hanbit.dump | head             # 덤프 목차 (테이블·인덱스·정책)
pg_restore -d hanbit --clean --if-exists --single-transaction hanbit.dump
pg_restore -d hanbit -t documents hanbit.dump  # 특정 테이블만 (인덱스·정책은 별도)
```

## 예상 면접 질문 5개 + 모범 답변

**Q1. RPO와 RTO를 설명해 주시고, 직접 측정해 본 적 있나요?**
> RPO는 장애가 났을 때 얼마 전 데이터까지 잃어도 되는지이고, 백업 주기가 결정합니다. RTO는 서비스를 얼마 만에 되살려야 하는지이고요. 직접 측정해 봤는데, 백업 직후에 데이터를 하나 더 넣고 문서 테이블을 실제로 지운 다음 최신 백업으로 복구했습니다. 장애부터 기능 확인까지 48초가 걸렸고, 백업부터 장애까지 36초 동안 넣은 데이터는 실제로 사라졌습니다. 데이터가 500KB 정도라 빨랐던 거고, 실제 고객 규모라면 덤프 크기와 인덱스 재생성 시간 때문에 훨씬 길어지니까 그 규모로 다시 재 봐야 한다고 생각합니다.

**Q2. 복제나 RAID가 있으면 백업이 필요 없지 않나요?**
> 아니라고 생각합니다. 복제와 RAID는 하드웨어 고장에 대비한 거라, 누가 실수로 테이블을 지우거나 랜섬웨어가 데이터를 암호화하면 그것도 그대로 복제됩니다. 백업은 과거 시점으로 되돌릴 수 있는 별도 사본이라 목적이 다릅니다. 그래서 운영에서는 둘 다 두고, 백업은 3-2-1 원칙으로 다른 장소에도 하나 두는 게 기본이라고 알고 있습니다.

**Q3. 랜섬웨어에 대비한 백업은 어떻게 해야 하나요?**
> 랜섬웨어는 운영 서버뿐 아니라 백업 서버까지 찾아서 지우거나 암호화하는 경우가 많아서, 정해진 기간 동안 관리자도 지울 수 없는 불변 백업이 핵심입니다. MinIO의 Object Lock, 엑사그리드의 시간 잠금 계층, Veeam의 Hardened Repository가 그런 기능으로 알고 있습니다. 그리고 백업 저장소의 계정을 운영 계정과 분리하고, 오프사이트 사본을 두고, 정기적으로 복구 훈련을 해서 실제로 되살아나는지 확인해야 합니다. 제 프로젝트는 일반 버킷에 저장해서 불변 설정까지는 못 했고, 그 부분을 후속 과제로 적어 뒀습니다.

**Q4. 쿠버네티스 환경에서는 무엇을 백업해야 하나요?**
> 크게 세 가지라고 봅니다. 첫째, 상태 데이터인 DB와 오브젝트 스토리지, 볼륨입니다. 둘째, 쿠버네티스 리소스 정의인데, 이건 git에 차트와 값으로 있으면 거기서 재현할 수 있습니다. 셋째, Secret처럼 git에 둘 수 없는 것들은 별도 비밀 관리 도구가 원본이 돼야 합니다. 저는 DB는 pg_dump로 MinIO에 매일, 설정은 Helm 값과 매니페스트를 내보냈고, Secret 값은 평문 유출 위험 때문에 일부러 빼고 목록만 남겼습니다. 운영이라면 Velero 같은 도구로 리소스와 볼륨 스냅샷을 함께 백업하는 걸 검토하겠습니다.

**Q5. 백업이 실패하면 어떻게 알 수 있나요?**
> 백업 CronJob의 마지막 성공 시각을 지표로 보고, 24시간 넘게 성공이 없으면 critical 알람이 울리게 했습니다. 실제로 백업 직후에 "마지막 성공 후 82초"로 잡히는 걸 확인했고요. 실패 자체를 잡는 Job 실패 알람도 따로 있습니다. 백업은 조용히 실패하는 게 제일 위험하다고 생각해서, 성공했다는 신호가 끊기는 걸 감시하는 방식으로 만들었습니다.

## 꼬리 질문 3개 + 답변 방향
1. **"pg_dump를 슈퍼유저로 한 이유는?"** → RLS가 켜진 테이블은 일반 계정으로 덤프하면 정책 때문에 일부 행만 보인다. pg_dump는 이를 막으려고 row_security=off로 실행하고, 권한이 없으면 오류를 낸다. 백업 전용 계정을 만들려면 BYPASSRLS 권한이 필요하다(최소 권한과의 트레이드오프).
2. **"벡터DB는 원본 문서로 다시 만들 수 있는데 백업해야 하나요?"** → 재생성이 가능해도 임베딩에 시간이 걸린다(이번에는 138청크 63초, 수십만 청크면 수 시간 이상). RTO를 지키려면 백업하는 게 맞다. 단, 임베딩 모델 버전과 차원이 같아야 쓸 수 있으니 모델 버전도 함께 기록한다.
3. **"백업 파일이 손상됐는지는 어떻게 알아요?"** → 체크섬 검증, `pg_restore -l`로 목차 읽기, 그리고 가장 확실한 건 정기 복구 훈련(별도 환경에 실제 복구 후 행 수·기능 확인)이다.
