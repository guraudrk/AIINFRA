# 08. 장애 대응 — 증상에서 근본 원인까지

## 한 줄 요약
장애 8개를 Helm 값으로 주입하고, 그중 4개(OOMKilled, 잘못된 모델 이름, GPU 부족 Pending, 권한 필터 유출)는 **고객 문의만 받고 직접 명령어로 원인을 찾았다.** 나머지는 시연과 앞 모듈의 실측으로 대신했다. 시나리오마다 런북을 남기고, 권한 유출은 고객 보고서 형식으로 작성했다.

## 용어 풀이 (비전공자용)
> 비유 기준: 클러스터 = 병원. 이번에는 **응급 상황 훈련**이다. 환자 증상(고객 문의)만 듣고 검사(명령어)로 병명(근본 원인)을 찾는다.

| 용어 | 쉬운 설명 | 비유 |
|---|---|---|
| **증상 vs 근본 원인** | 증상은 겉으로 보이는 현상(답이 안 옴), 근본 원인은 그걸 만든 진짜 이유(메모리 상한을 잘못 줄임) | 열이 난다 vs **감염** |
| **장애 주입 (Chaos)** | 일부러 장애를 일으켜 진단·복구 절차를 훈련하는 것 | **소방 훈련** |
| **런북 (Runbook)** | 장애 유형별 "증상 → 확인 명령 → 원인 → 조치 → 재발 방지" 대응 문서 | 응급실 **처치 매뉴얼** |
| **Exit Code** | 프로세스가 끝날 때 남기는 번호. 0=정상, 1=앱 오류, **137=SIGKILL(128+9, 보통 OOMKilled)**, **143=SIGTERM(128+15, 정상 종료 요청)** | 퇴원 사유 코드 |
| **OOMKilled** | 메모리 상한을 넘어 커널이 강제로 죽인 것 | 정원 초과로 **강제 퇴실** |
| **CrashLoopBackOff** | 계속 죽고 재시작하기를 반복해, 재시작 간격이 점점 늘어나는 상태 | 쓰러졌다 일어나기를 반복 → 회복 대기 시간이 길어짐 |
| **Pending** | 들어갈 노드를 못 찾아 대기 중 | 대기실 |
| **READY 0/1** | 프로세스는 살아 있지만 준비 검사(readiness)를 통과 못 해 트래픽을 안 받는 상태 | 출근은 했는데 **진료 준비가 안 돼** 환자를 안 받음 |
| **롤백** | 문제가 생긴 배포를 이전 상태로 되돌리는 것 | 수술 전 상태로 되돌리기 |
| **장애 보고서 (Postmortem)** | 타임라인, 영향, 근본 원인, 임시·영구 조치, 후속 과제를 정리한 문서. 사람을 탓하지 않고 구조를 고친다(blameless) | 사고 **경위서 + 재발 방지 대책** |
| **MTTD / MTTR** | 장애를 알아차리기까지 시간 / 복구까지 시간 | 발견 시간 / 회복 시간 |

## 핵심 개념
- **진단 순서는 넓은 데서 좁은 데로**: ① 고객 증상을 기능 경로로 바꾼다(게이트웨이 → 임베딩 → DB → LLM) ② `kubectl get pods`로 이상 징후(STATUS, READY, RESTARTS, AGE) ③ `describe`의 Last State·Events ④ `logs`(재시작됐으면 `--previous`) ⑤ "언제부터"를 변경 이력(Helm history, 배포 기록)과 맞춘다.
- **Pod 상태별 첫 질문**
  | 상태 | 먼저 볼 것 |
  |---|---|
  | Pending | describe → `FailedScheduling` 메시지 (자원 부족, taint, selector, PVC) |
  | ContainerCreating 오래 | Events → 이미지 pull, 볼륨 마운트, Secret 없음 |
  | ImagePullBackOff | 이미지 이름·태그, 레지스트리 접근(폐쇄망이면 반입 누락) |
  | Running + READY 0/1 | readiness probe 실패 메시지 |
  | CrashLoopBackOff | `logs --previous`, Last State의 Exit Code(137=OOM, 1=앱 오류) |
  | Running인데 느림 | `kubectl top`, CPU throttling(limit), 대기열 지표 |
- **"원래 있던 오류"를 원인으로 착각하지 않는다**: 시점(증상 시작과 맞는가)과 경로(고객 기능의 경로에 있는가)를 같이 본다.
- **배포 성공 ≠ 서비스 정상**: Helm은 설정을 넣으면 성공이다. `--wait`와 자동 롤백, 배포 후 확인이 필요하다.
- 비유: 응급실 의사가 증상(열)을 듣고, 활력 징후(get pods) → 정밀 검사(describe, logs) → 병력(변경 이력) 순으로 좁혀서 병명(근본 원인)을 찾는다. 처치 후에는 **경위서**(장애 보고서)와 **매뉴얼**(런북)을 남긴다.

## 이 프로젝트에서 내가 한 것
- **장애 주입 스크립트** `scripts/chaos/0N-*.sh inject|revert` (`make chaos SCENARIO=N`). 장애는 Helm 값으로만 주입했다(kubectl 직접 수정 금지, M4 교훈). 각 장애는 **고객 문의 형태로 증상만** 받고 시작했다.
- **직접 진단한 4개**
  | # | 고객 증상 | 내가 본 것 | 근본 원인 |
  |---|---|---|---|
  | 1 | 질문하면 기다리다 오류 | `describe` Last State: **OOMKilled / Exit 137** → Helm 이력 | 메모리 limit을 512Mi로 줄인 배포 (모델 1.9GB) |
  | 2 | 업그레이드 후 답 못 함, 배포는 성공 | READY **0/1** → Events: `Readiness probe failed: model 'qwen2.5:3b-instruct-q8' not found` | PVC에 없는 모델 이름 (폐쇄망이라 다운로드도 불가) |
  | 3 | GPU 증설 후 응답 없음, 노드 정상 | **Pending** → `0/4 nodes: 1 Insufficient nvidia.com/gpu, 2 untolerated taint ...` | GPU 3개 요청 > 용량 2개, Recreate 전략이라 LLM 0개 |
  | 7 | 보안팀: 품질 문서 유출 여부 조사 | `APP_FILTER_ENABLED=false` → 감사 로그(작업자 질의 `doc_ids={}`) → 앱 계정 직접 조회(작업자 0 / 품질 25) | 디버깅 설정이 운영 배포에 포함. **RLS가 막아 유출 없음** |
  - 시나리오 1에서 처음에는 63분 전에 생긴 수집 Job의 Error를 원인으로 짚었다. **시점(AGE)과 경로**가 안 맞는다는 피드백을 받고, 힌트(`describe`의 Last State)로 OOMKilled를 찾았다.
- **시연한 것**
  - 4 DB 다운: postgres-0 강제 삭제 → 게이트웨이 readyz 503 → **약 9초 뒤** 같은 이름·같은 디스크로 재생성 → 게이트웨이가 **재시작 없이 재연결**(200)
  - 5 임베딩 교체: 생성 모델을 임베딩에 지정하자 LLM 서빙이 **501(임베딩 미지원)**. 차원 불일치는 1024차원 청크에 768차원 질문 벡터로 검색해 **`different vector dimensions 1024 and 768`** 확인
  - 6 요청 폭주: M6 실측(대기열 5 > 슬롯 4 → TTFT p95 약 1분, 알람 firing)으로 대체
  - 8 데이터 유실: M7 복구 훈련(RTO 48초, RPO 36초)으로 대체
- **훈련 도구 자체에서 겪은 문제**: 원복 스크립트가 `helm upgrade`만 해서 **직전 `--set` 값이 다시 적용**됐다. "원복 배포 성공"인데 장애 설정이 그대로였다. `--reset-values`를 명시하고, 원복 뒤 덮어쓴 값이 남았는지 검증하도록 고쳤다. 시나리오 2의 교훈(배포 성공 ≠ 정상)을 내가 그대로 겪은 셈이다.
- 산출물: `runbooks/01~08-*.md`(실제 출력 포함), `docs/incident-report-sample.md`(시나리오 7 고객 보고서)

## 실제 기업 환경에서는
- **장애 대응 절차**: 접수 → 등급 판정(영향 범위·긴급도) → 고객 1차 공지(인지했고 조사 중) → 진단 → 임시 조치(서비스 복구 우선) → 근본 원인 → 영구 조치 → 보고서. 등급별로 응답 시간(SLA)이 정해져 있다.
- **고객 커뮤니케이션**: 추측을 사실처럼 말하지 않는다. 확인된 것 / 조사 중인 것 / 다음 공지 시각을 구분해서 정해진 주기로 알린다. 기술 용어 대신 영향(무엇을 못 쓰는지, 데이터는 안전한지)부터 말한다.
- **리눅스·하드웨어 점검**: 쿠버네티스 밖도 본다. `dmesg`(OOM, Xid), `journalctl -u kubelet`, `top`/`free`/`df`/`iostat`, `ss -tulnp`, NTP, BMC 이벤트 로그. GPU는 `nvidia-smi`, DCGM 진단.
- **재발 방지는 구조로**: 사람의 실수를 탓하지 않고 배포 파이프라인 검사, 자동 롤백, 알람, 런북으로 막는다.

## 에티버스그룹 사업과의 연결
이테크시스템의 통합 구축 범위에는 **유지보수와 장애 대응**이 들어 있다. 고객사 엔지니어는 "AI가 답을 안 해요" 같은 증상만 전달하는 경우가 많다. 그걸 GPU·스토리지·네트워크·플랫폼 계층으로 나눠 좁히는 절차와 런북, 그리고 보안 사고 시 감사 로그로 **"유출이 없었다"를 증명하는 보고서**가 고객 신뢰를 지키는 실무라고 생각한다.

## 자주 쓰는 명령어
```bash
kubectl get pods -A -o wide | grep -vE "Running|Completed"   # 이상 Pod만
kubectl describe pod <pod> | grep -A6 "Last State"           # 직전 종료 사유 (OOMKilled / Exit Code)
kubectl describe pod <pod> | sed -n '/Events:/,$p'           # 스케줄링·probe 실패 메시지
kubectl logs <pod> --previous                                # 재시작 전 컨테이너 로그
kubectl get events -n ai-platform --sort-by=.lastTimestamp | tail
kubectl top pod -n ai-platform --containers                  # CPU·메모리 (throttling 의심)
kubectl describe node <node> | grep -A8 "Allocated resources"
helm history ai-platform -n ai-platform                      # "언제 무엇이 바뀌었나"
helm get values ai-platform -n ai-platform                   # 덮어쓴 값
helm upgrade ... --reset-values                              # 차트 기본값으로 확실히 원복
make chaos SCENARIO=N / make chaos-revert SCENARIO=N
```

## 예상 면접 질문 5개 + 모범 답변

**Q1. 고객이 "AI가 답을 안 해요"라고 하면 어떻게 대응하시겠어요?**
> 먼저 증상을 구체화합니다. 로그인이나 화면은 되는지, 언제부터인지, 전원이 안 되는지 일부만 안 되는지요. 그다음 요청 경로인 입구, 게이트웨이, 임베딩, DB, LLM 순으로 Pod 상태를 보고, 이상한 Pod가 있으면 describe의 Last State와 Events, 로그를 봅니다. 마지막으로 그 시점에 무엇이 바뀌었는지 배포 이력과 맞춰 봅니다. 실제로 훈련할 때 처음에 오래전부터 있던 다른 Job 오류를 원인으로 잘못 짚었는데, 시점과 경로가 맞지 않는다는 걸 확인하고 LLM Pod의 OOMKilled를 찾았습니다. 그 경험 이후로 "언제부터, 어느 경로"를 꼭 같이 봅니다.

**Q2. Exit Code 137, 1, 143은 각각 무엇인가요?**
> 137은 128 더하기 9라서 SIGKILL로 강제 종료된 거고, 쿠버네티스에서는 대부분 메모리 limit 초과로 커널이 죽인 OOMKilled입니다. 1은 애플리케이션이 오류로 스스로 종료한 경우라 로그를 봐야 하고요. 143은 128 더하기 15, SIGTERM이라 정상적인 종료 요청을 받은 겁니다. 배포나 스케일 다운 때 흔히 봅니다. 저는 LLM 메모리 limit을 모델보다 작게 줄인 장애에서 OOMKilled에 137을 직접 확인했습니다. 반대로 CPU limit 초과는 죽지 않고 느려지기만 해서, Grafana가 응답이 없을 때 kubectl top으로 throttling을 찾은 적도 있습니다.

**Q3. Pod가 Running인데 서비스가 안 됩니다. 무엇을 의심하나요?**
> READY 열을 봅니다. Running인데 0/1이면 프로세스는 살아 있지만 준비 검사에 실패해서 Service가 트래픽을 보내지 않는 상태입니다. 모델 업그레이드 장애 훈련에서 정확히 이랬는데, Events에 "모델을 찾을 수 없다"는 readiness 실패 메시지가 있었습니다. 배포 도구는 성공으로 나왔지만, 그건 설정이 클러스터에 들어갔다는 뜻이지 앱이 준비됐다는 뜻이 아니어서, 배포할 때 wait와 자동 롤백을 써야 한다고 정리했습니다.

**Q4. 보안 사고가 의심될 때는 어떻게 조사하고 보고하나요?** ★
> 세 가지를 순서대로 답하려고 합니다. 무엇이 바뀌었는지, 실제로 피해가 있었는지, 누가 무엇을 했는지요. 권한 필터가 꺼진 배포를 조사할 때 먼저 설정에서 필터 비활성화를 확인했고, 감사 로그에서 작업자 계정이 품질 문서를 노린 질문을 한 기록을 찾았는데 사용된 문서가 0건이었습니다. 왜 막혔는지도 DB에 직접 같은 조건으로 조회해서, 행 수준 보안이 작업자에게 품질 문서를 0건으로 보여 주는 걸 증명했습니다. 보고서에는 타임라인, 영향 범위, 근본 원인, 임시·영구 조치와 고객 공유 문구를 넣었고, "유출 없음"을 추측이 아니라 감사 로그와 DB 검증으로 말할 수 있게 했습니다.

**Q5. 장애 재발을 막으려면 무엇을 해야 하나요?**
> 사람을 탓하기보다 구조를 고쳐야 한다고 생각합니다. 이번에 찾은 원인들은 모두 배포 변경이었는데요, 메모리 축소, 없는 모델 이름, 과도한 GPU 요청, 보안 설정 비활성화였습니다. 그래서 배포할 때 준비 실패 시 자동 롤백, 권한 자동 테스트 필수화, 보안 설정 값 정책 검사, 그리고 재시작이나 권한 거부 급증 알람을 재발 방지책으로 정했습니다. 저도 원복 스크립트가 이전 값을 다시 적용하는 실수를 했는데, 원복 후 실제 값을 검증하도록 고쳤습니다. 확인 단계를 자동화하는 게 제일 확실하다고 봅니다.

## 꼬리 질문 3개 + 답변 방향
1. **"OOMKilled가 나면 메모리만 늘리면 되나요?"** → 먼저 왜 늘었는지 본다. 설정 실수(이번 경우)인지, 정상적인 사용량 증가(컨텍스트·동시 요청 증가 → KV 캐시)인지, 메모리 누수인지. 모델 크기 공식으로 필요량을 계산해 근거 있게 정하고, 노드 여유도 확인한다.
2. **"Recreate와 RollingUpdate 중 무엇을 써야 하나요?"** → 무중단에는 RollingUpdate가 좋지만, GPU처럼 자원이 딱 맞으면 새 Pod가 Pending이 되어 롤링이 멈춘다. RWO 볼륨도 동시에 붙이기 어렵다. 그래서 GPU 서빙은 Recreate를 쓰거나 여유 GPU를 두고, 레플리카를 2개 이상 두어 하나씩 교체한다.
3. **"장애 중 고객에게 뭐라고 말하나요?"** → 확인된 사실, 조사 중인 것, 다음 공지 시각을 구분한다. 원인 추측은 확인 전에 단정하지 않는다. 영향(무엇이 안 되는지, 데이터는 안전한지)을 먼저 말한다.
