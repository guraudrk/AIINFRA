## 00. 환경 — WSL2, 컨테이너, GPU 드라이버 스택

📘 노트: [00-environment.md](study/00-environment.md) · 개념서: [01-foundations.md](textbook/01-foundations.md)

### Q1. 컨테이너와 VM의 차이를 설명해 주세요.

**답변 (30~45초)** — VM은 하이퍼바이저 위에 게스트 OS를 통째로 하나 더 올리는 방식이고, 컨테이너는 호스트 커널을 같이 쓰면서 리눅스 namespace로 프로세스, 네트워크, 파일시스템을 격리하고 cgroup으로 CPU나 메모리를 제한하는 방식입니다. 그래서 컨테이너가 훨씬 가볍고 빨리 뜨지만, 커널을 공유하니까 격리 수준은 VM보다 약합니다. 이번 프로젝트에서 쓰는 kind도 쿠버네티스 노드를 VM이 아니라 Docker 컨테이너로 띄우는 도구라서, 16GB PC 한 대에서 4노드 클러스터를 구성할 수 있습니다.

### Q2. 컨테이너에서 GPU를 쓰려면 무엇이 필요한가요?

**답변 (30~45초)** — 세 층으로 이해하고 있습니다. 호스트에 NVIDIA 드라이버, 컨테이너 이미지 안에 CUDA 런타임, 그리고 그 둘을 이어 주는 NVIDIA Container Toolkit입니다. Toolkit이 컨테이너를 만들 때 호스트의 드라이버 라이브러리와 /dev/nvidia 장치를 컨테이너에 넣어 주는 역할을 합니다. 그래서 드라이버는 호스트에 한 번만 깔고, CUDA 버전은 이미지마다 달라도 되는데, 단 드라이버가 그 CUDA 버전보다 같거나 새 버전이어야 합니다. 저는 실제로 `docker run --gpus all ... nvidia-smi`로 컨테이너 안에서 GPU가 보이는지 확인하고 시작했습니다.

### Q3. 고객사에 GPU 서버가 들어왔다면, 서비스 올리기 전까지 어떤 순서로 작업하나요?

**답변 (30~45초)** — 실장과 전원·케이블링 다음에 먼저 iDRAC이나 iLO 같은 BMC를 관리망에 연결해서 원격으로 전원이나 콘솔, 펌웨어 업데이트를 할 수 있게 해 둡니다. 그다음 OS를 깔고, 드라이버·CUDA·Container Toolkit 순으로 올린 뒤에, 쿠버네티스나 OpenShift를 구성하고 GPU Operator로 device plugin이랑 DCGM exporter를 배포합니다. 마지막으로 모니터링을 붙이고 DCGM 진단이나 부하 테스트로 인수 테스트를 합니다. 다만 실제 랙 작업이나 BMC 설정은 제가 아직 현장에서 해 본 적은 없어서, 순서와 목적을 이해한 수준이라고 말씀드리는 게 정확할 것 같습니다.

### Q4. WSL2로 연습한 환경이 실제 서버와 어떻게 다른가요?

**답변 (30~45초)** — 커널과 도구는 진짜 리눅스라서 kubectl, helm, 셸 스크립트 같은 건 서버랑 그대로 같습니다. 차이는 하드웨어 계층인데요, WSL에서는 GPU 드라이버가 Windows에 설치되어 있고 WSL은 그걸 공유받는 구조라서, 베어메탈처럼 커널 모듈을 직접 설치하거나 BMC, NVLink, ECC 같은 걸 다룰 수는 없습니다. 실제로 이번에 보니 Windows 화면이 VRAM을 5GB 넘게 쓰고 있어서, 서버였다면 신경 쓰지 않아도 될 제약 때문에 모델을 3B로 줄였습니다. 그래서 문서에 실제 환경과의 차이를 따로 적어 두었습니다.

### Q5. GPU 메모리를 보고 어떻게 모델 크기를 정했나요?

**답변 (30~45초)** — 가중치 메모리는 대략 파라미터 수 곱하기 파라미터당 바이트로 계산했습니다. 7B를 FP16으로 올리면 14GB라 8GB 카드에는 안 들어가고, 4비트 양자화면 3.5GB 정도인데 저는 여유 VRAM이 3GB밖에 없었습니다. 그래서 3B 모델의 4비트 버전, 약 1.9GB를 골랐고, 남는 공간이 KV 캐시랑 임베딩 모델 몫입니다. 실제 속도는 다음 단계에서 동시 요청별 TTFT와 초당 토큰으로 측정해서 근거를 남길 계획입니다.

## 01. 쿠버네티스 클러스터 — 노드 역할 분리와 GPU 스케줄링

📘 노트: [01-cluster.md](study/01-cluster.md) · 개념서: [02-kubernetes.md](textbook/02-kubernetes.md)

### Q1. 쿠버네티스 구성요소를 설명해 주세요.

**답변 (30~45초)** — 크게 컨트롤 플레인과 워커 노드로 나뉩니다. 컨트롤 플레인에는 모든 요청을 받는 API 서버, 클러스터 상태를 저장하는 etcd, Pod를 어느 노드에 둘지 정하는 스케줄러, 원하는 상태를 맞춰 주는 컨트롤러 매니저가 있습니다. 워커 노드에는 컨테이너를 실제로 띄우는 kubelet, 서비스 트래픽 규칙을 만드는 kube-proxy, 그리고 containerd 같은 런타임이 있습니다. 제 프로젝트에서는 kind로 컨트롤 플레인 1대, 워커 3대를 만들었는데요, 운영 환경이라면 etcd quorum 때문에 컨트롤 플레인을 3대 이상으로 두는 게 기본이라고 알고 있습니다.

### Q2. taint/toleration과 nodeSelector(affinity)의 차이는 뭔가요? GPU 노드에는 뭘 써야 하나요?

**답변 (30~45초)** — nodeSelector는 Pod가 특정 노드로 가겠다고 끌어당기는 거고, taint는 노드가 허락 안 한 Pod를 밀어내는 겁니다. GPU 노드는 둘 다 필요하다고 생각합니다. taint만 걸면 GPU Pod가 다른 데로 갈 수도 있고, nodeSelector만 쓰면 일반 Pod가 비싼 GPU 노드를 차지할 수 있어서요. 실제로 GPU 노드에 `nvidia.com/gpu=present:NoSchedule` taint를 걸고 toleration 없는 GPU Pod를 띄워 봤는데, Pending이 되면서 "3개 노드는 taint 때문에, 1개는 GPU 부족으로 안 된다"는 메시지가 그대로 나왔습니다.

### Q3. Pod가 GPU를 요청했는데 Pending입니다. 어떻게 확인하시겠어요?

**답변 (30~45초)** — 먼저 `kubectl describe pod`로 Events의 FailedScheduling 메시지를 봅니다. 노드별 탈락 이유가 나오니까요. "Insufficient nvidia.com/gpu"면 `describe node`에서 GPU가 Capacity에 잡혀 있는지, 다른 Pod가 이미 다 쓰고 있는지(Allocated resources) 봅니다. Capacity에 아예 없으면 device plugin Pod가 죽었거나 드라이버 문제일 수 있어서 device plugin 로그랑 노드에서 `nvidia-smi`를 확인하겠습니다. "untolerated taint"면 Pod 스펙에 toleration이 빠진 거고요. 제가 이 순서를 실제로 해 봤는데, 테스트 Pod로 Pending을 일부러 만들어서 확인했습니다.

### Q4. device plugin과 GPU Operator는 각각 뭘 하나요?

**답변 (30~45초)** — device plugin은 노드의 GPU를 찾아서 kubelet에 "GPU 몇 개 있다"고 등록하고, Pod가 GPU를 받으면 그 GPU 장치만 컨테이너에 넣어 주는 역할입니다. GPU Operator는 그걸 포함해서 드라이버, Container Toolkit, GPU 정보를 라벨로 붙이는 Feature Discovery, DCGM 모니터링까지 한꺼번에 설치·관리해 주는 도구입니다. 제 PC는 WSL이라 device plugin이 GPU를 제대로 못 잡을 위험이 있어서, 노드 status에 GPU 2개를 API로 직접 등록하는 방식으로 대신했습니다. 스케줄링 동작은 똑같이 검증되지만 Pod 안에 실제 GPU가 들어가진 않는다는 차이는 분명히 말씀드리고 싶습니다.

### Q5. kind로 만든 클러스터와 실제 운영 클러스터는 뭐가 다른가요?

**답변 (30~45초)** — kind는 노드를 Docker 컨테이너로 띄워서 PC 한 대로 멀티 노드를 흉내 내는 테스트용 도구입니다. 운영 환경은 OpenShift나 RKE2처럼 지원되는 배포판을 쓰고, 컨트롤 플레인을 3대 이상 HA로 구성하고, 앞단에 로드밸런서를 둡니다. 스토리지도 kind는 노드 로컬 디스크를 쓰지만 운영에서는 외부 스토리지를 CSI로 붙이고, GPU도 실제 장비에 GPU Operator를 씁니다. 그래서 저는 kind로 개념과 스케줄링 동작을 검증했고, 운영 환경 구성은 문서로 정리하면서 차이를 따로 기록해 두었습니다.

## 02. sLLM·임베딩 서빙 — 모델 크기, 메모리, 성능 지표

📘 노트: [02-llm-serving.md](study/02-llm-serving.md) · 개념서: [03-llm-serving.md](textbook/03-llm-serving.md)

### Q1. 7B 모델을 서빙하려면 GPU 메모리가 얼마나 필요한가요?

**답변 (30~45초)** — 가중치는 파라미터 수 곱하기 파라미터당 바이트라서, FP16이면 7B × 2바이트로 약 14GB, INT4로 양자화하면 3.5GB 정도입니다. 그런데 이건 모델만 올린 거고, 실제로는 동시 사용자 수 × 컨텍스트 길이만큼 KV 캐시가 더 들고 런타임 여유분도 필요합니다. 그래서 FP16 7B를 여러 명이 쓰려면 24GB 카드는 빠듯하고 40~48GB급을 보는 게 안전하다고 생각합니다. 저는 이 공식으로 제 PC용 3B 모델 메모리를 계산해서 쿠버네티스 requests/limits에 근거와 함께 적어 두었습니다.

### Q2. TTFT와 토큰/초는 각각 무엇이고 왜 따로 봐야 하나요?

**답변 (30~45초)** — TTFT는 질문을 보내고 첫 글자가 나오기까지 시간이고, 토큰/초는 그 뒤에 답이 써지는 속도입니다. TTFT는 입력 길이와 대기열에 영향을 많이 받아서, RAG처럼 참고 문서를 길게 넣거나 동시 사용자가 몰리면 확 늘어납니다. 토큰/초는 모델 크기와 GPU 메모리 대역폭에 좌우되고요. 사용자 체감은 TTFT가 크게 좌우해서 알람도 TTFT p95로 거는 게 맞다고 봤고, 동시 요청 1, 4, 8개에서 둘 다 측정해 봤습니다.

### Q3. 양자화를 하면 무엇을 얻고 무엇을 잃나요?

**답변 (30~45초)** — 메모리가 줄어서 같은 GPU에 더 큰 모델을 올리거나 동시 사용자를 늘릴 수 있고, 메모리 대역폭 부담이 줄어서 대체로 생성 속도도 빨라집니다. 대신 정확도가 조금 떨어지는데, 4비트까지 내리면 한국어나 전문 용어에서 차이가 보일 수 있다고 알고 있습니다. 그래서 실무에서는 고객 업무 질문 세트로 FP16과 INT8, INT4 답변 품질을 비교해 보고 결정해야 한다고 생각합니다. 저는 이번에 메모리 제약 때문에 4비트를 썼고, 품질 비교까지는 아직 못 해 봤습니다.

### Q4. Ollama, vLLM, Triton은 어떻게 다르고 언제 무엇을 쓰나요?

**답변 (30~45초)** — Ollama는 설치가 쉽고 CPU에서도 돌아서 개발이나 소규모 용도에 좋습니다. vLLM은 PagedAttention과 continuous batching 덕분에 GPU에서 동시 요청이 많을 때 처리량이 훨씬 높아서 운영용 LLM 서빙에 많이 씁니다. Triton은 NVIDIA의 범용 추론 서버라서 LLM뿐 아니라 비전 모델 같은 여러 모델을 한 서버에서 같이 운영할 때 씁니다. 제 PC는 GPU를 쿠버네티스에 붙이지 못해서 Ollama로 했고, 차트에는 GPU 환경에서 vLLM으로 바꿀 수 있는 옵션을 넣어 뒀는데 그건 실제로 돌려 보진 못했습니다.

### Q5. 쿠버네티스에서 GPU는 왜 limits로만 요청하고, 여러 Pod가 GPU 하나를 나눠 쓰려면 어떻게 하나요?

**답변 (30~45초)** — GPU 같은 확장 리소스는 오버커밋이 안 되고 정수로 통째로 할당돼서, limits만 쓰면 requests도 같은 값으로 잡힙니다. 그래서 기본적으로는 Pod 하나가 GPU 한 장을 독점합니다. 나눠 쓰려면 세 가지 방법이 있는데요, A100·H100에서는 MIG로 GPU를 물리적으로 최대 7개로 쪼갤 수 있고, time-slicing은 시간을 나눠 번갈아 쓰는 방식이라 격리가 약하고, MPS는 여러 프로세스가 동시에 쓰게 해 줍니다. 운영 환경에서 격리가 중요하면 MIG, 개발 환경이면 time-slicing을 고려하겠습니다.

### 보너스 Q. 배포했는데 Pod가 계속 NotReady입니다. 어떻게 접근하셨나요?

**답변 (30~45초)** — 실제로 겪었는데요, 모델을 받는 Job이 10분 넘게 "서버 대기"만 하고 있었습니다. 바로 고치지 않고 먼저 모델 폴더 크기를 봤더니 16KB 그대로라서 다운로드가 시작도 안 된 걸 알았고, 서버 로그에도 다운로드 요청이 없었습니다. 그래서 Service 엔드포인트를 보니 ready가 false였습니다. Service는 Ready Pod에만 트래픽을 보내는데, 제가 readiness를 "모델이 있어야 통과"로 만들어서 모델을 넣으려는 요청이 못 들어가는 교착 상태였던 거죠. 사용자용 Service는 그대로 두고, NotReady Pod에도 연결되는 관리용 Service를 따로 만들어서 해결했습니다.

## 03. 데이터 계층 — 스토리지, 벡터DB, 수집 파이프라인

📘 노트: [03-data-layer.md](study/03-data-layer.md) · 개념서: [04-storage-data.md](textbook/04-storage-data.md)

### Q1. 블록, 파일, 오브젝트 스토리지의 차이와 AI 플랫폼에서의 용도를 설명해 주세요.

**답변 (30~45초)** — 블록은 디스크를 블록 단위로 OS에 그대로 붙여 주는 방식이라 DB처럼 빠른 랜덤 읽기·쓰기에 쓰고, 파일은 NAS처럼 폴더 구조로 여러 서버가 공유할 때 쓰고, 오브젝트는 파일을 키로 통째로 저장해서 용량을 거의 무한히 늘릴 수 있어 원본 데이터나 백업에 씁니다. 제 프로젝트에서는 원본 문서는 S3 호환인 MinIO에 두고, 검색용 청크와 벡터는 PostgreSQL에 블록 스토리지로 뒀습니다. 학습까지 하는 GPU 클러스터라면 여기에 고성능 병렬 파일시스템이 추가된다고 알고 있습니다.

### Q2. RAG에서 문서를 왜 청크로 자르고, 크기와 겹침은 어떻게 정했나요?

**답변 (30~45초)** — LLM 컨텍스트에 문서 전체를 넣을 수 없고, 넣더라도 관련 없는 내용이 섞이면 답이 흐려지니까 관련 조각만 찾아서 넣으려고 자릅니다. 저는 글자 수로만 자르지 않고 매뉴얼의 제목 단위, 그러니까 경보 코드 하나 단위로 잘랐습니다. 그래야 원인, 조치, 부품이 한 조각에 같이 들어가거든요. 그래도 길면 700자 단위로 100자씩 겹쳐서 경계 문장이 안 잘리게 했고, 조각마다 앞에 문서 제목과 섹션 이름을 붙여서 조각만 봐도 어떤 설비 내용인지 알 수 있게 했습니다.

### Q3. 벡터DB 저장 용량은 어떻게 계산하나요?

**답변 (30~45초)** — 벡터만 보면 청크 수 곱하기 차원 수 곱하기 4바이트(float32)입니다. 제 경우 청크 138개에 1024차원이라 약 0.56MB였고, 실제 테이블은 본문까지 2MB, HNSW 인덱스가 1.1MB 정도 나왔습니다. 고객사 문서가 2만 건이고 문서당 청크가 수십 개면 수십만 청크라 벡터만 수 GB가 되고, HNSW 인덱스는 메모리에 올라가야 빨라서 DB 서버 메모리도 같이 잡아야 합니다. 이 계산식은 사이징 계산기에도 넣을 계획입니다.

### Q4. 의미 검색만으로 충분하지 않은 경우가 있나요?

**답변 (30~45초)** — 네, 실제로 겪었습니다. "E-203"이라고만 검색했더니 프레스 4호기 매뉴얼이 3호기보다 위에 나왔는데요, 다섯 대 매뉴얼의 E-203 내용이 거의 같아서 벡터로는 구분이 안 된 겁니다. 그래서 호기나 문서 등급처럼 정확히 걸러야 하는 조건은 메타데이터 필터로 처리하고, 경보 코드 같은 고유 기호는 키워드 검색을 같이 쓰는 하이브리드 방식이 필요하다고 판단했습니다. 또 권한 필터 없이 검색하면 품질팀 전용 보고서가 1위로 나와서, 권한 필터도 반드시 검색 단계에서 걸어야 한다는 걸 확인했습니다.

### Q5. 비밀번호 같은 비밀값은 어떻게 관리했나요?

**답변 (30~45초)** — 코드나 Git에는 하나도 안 넣었습니다. 스크립트가 openssl로 무작위 비밀번호를 만들어 쿠버네티스 Secret에 넣고, 이미 있으면 덮어쓰지 않게 했습니다. DB 초기화 스크립트도 비밀번호를 환경변수로만 받습니다. DB 계정도 관리자, 수집용, 앱용으로 나눠서 앱은 읽기와 감사 로그 쓰기만 하도록 최소 권한으로 줬습니다. 다만 쿠버네티스 Secret은 기본적으로 base64 인코딩일 뿐이라, 운영이라면 etcd 암호화나 Vault 같은 외부 비밀 관리 도구를 써야 한다고 알고 있습니다.

### 보너스 Q. 오픈소스 이미지가 갑자기 사라지면 어떻게 대응하시겠어요?

**답변 (30~45초)** — 이번에 MinIO 공식 커뮤니티 이미지가 Docker Hub에서 사라진 걸 겪었습니다. 먼저 일시적인 문제인지 확인하려고 Docker Hub API와 pull 오류 메시지를 봤더니 저장소 자체가 404였습니다. 대안으로 동결된 Bitnami 레거시 이미지, 소스에서 계속 빌드하는 Chainguard 이미지, 커뮤니티 포크, 다른 S3 호환 스토리지를 비교했고, 유지보수와 출처 신뢰성을 기준으로 Chainguard를 골라 digest로 고정했습니다. 고객 환경이라면 기술 지원과 보안 패치가 보장되는 상용판을 권하고, 폐쇄망이면 검증된 이미지를 내부 레지스트리에 보관해 두는 게 맞다고 생각합니다.

**꼬리 질문 키워드**: "StatefulSet과 Deployment + PVC는 뭐가 달라요?" / "HNSW 말고 다른 인덱스는요?" / "온톨로지 테이블은 어디에 쓰나요?"


## 04. 권한 기반 RAG + AI 에이전트 — 이 프로젝트의 핵심

📘 노트: [04-rag-agent.md](study/04-rag-agent.md) · 개념서: [05-rag-agent-security.md](textbook/05-rag-agent-security.md)

### Q1. RAG가 어떻게 동작하는지, 그리고 환각을 어떻게 줄였는지 설명해 주세요.

**답변 (30~45초)** — 질문을 임베딩해서 권한과 설비 조건으로 거른 문서 조각 중 가까운 걸 찾고, 그걸 LLM에게 같이 줘서 답하게 하는 방식입니다. 환각은 세 가지로 줄였는데요, 첫째로 근거 문서가 거리 기준을 못 넘으면 LLM을 아예 부르지 않고 "찾을 수 없다"고 답합니다. 그 기준값은 관련 질문과 무관한 질문의 거리를 실제로 재서 0.56으로 정했습니다. 둘째로 프롬프트에서 자료에 없는 건 추측하지 말라고 지시했고, 셋째로 출처는 LLM이 쓰게 하지 않고 앱이 검색 결과에서 직접 붙였습니다. 처음에 RAG 없이 물어봤을 때는 3B 모델이 없는 용어를 지어냈는데, 이 구조로 바꾼 뒤에는 무관한 질문에 "찾을 수 없습니다"로 답하는 걸 자동 테스트로 확인하고 있습니다.

### Q2. 권한 통제를 왜 앱과 DB 두 군데에 했나요?

**답변 (30~45초)** — 앱 필터만 있으면 코드 버그나 새로 추가한 기능 하나에서 필터를 빠뜨리는 순간 다 뚫리기 때문입니다. 그래서 DB에 행 수준 보안을 걸어서, 앱이 어떤 쿼리를 보내든 그 요청의 역할에 허용된 행만 보이게 했습니다. 실제로 앱을 거치지 않고 앱 계정으로 직접 조회해도 작업자 역할이면 품질 문서 청크가 0개로 나옵니다. 반대로 앱 쪽 검사는 "이 기능은 권한이 없어서 실행하지 않았다"고 사용자에게 설명하고 감사 로그에 거부 기록을 남기는 역할입니다. 앱은 설명과 기록, DB는 강제, 이렇게 역할을 나눴습니다.

### Q3. 에이전트는 어떻게 도구를 고르나요? LLM에게 맡기지 않은 이유는요?

**답변 (30~45초)** — 두 방식을 다 만들어서 비교했습니다. 기본은 규칙 기반인데, 질문에서 호기와 경보 코드, "이력", "재고" 같은 의도를 뽑아 도구를 정하고 LLM은 결과 요약만 합니다. LLM 도구 호출 모드도 옵션으로 넣어서 같은 4문항을 돌려 보니 둘 다 4개를 다 맞혔습니다. 3B 모델이 생각보다 잘 골랐지만, 도구를 고르는 데 LLM 호출이 한 번 더 들어서 짧은 질문은 5초에서 12초로 늘었습니다. 무엇보다 규칙 기반은 같은 질문에 늘 같은 도구를 쓰니까 권한 테스트와 감사가 예측 가능해서 기본값으로 뒀습니다. 다만 4문항으로 결론 내긴 이르다고 생각해서, 질문 세트를 늘려 다시 측정해 보고 싶습니다.

### Q4. ERP 권한 운영 경험이 이 프로젝트에 어떻게 쓰였나요?

**답변 (30~45초)** — 제조기업 IT팀에서 국내외 법인 계정과 권한을 운영했고, 권한 요청을 "요청-검토-반영-이력 관리" 절차로 표준화해서 누락률을 0%대로 낮췄습니다. **[✏️ 직접 채우기: 표준화 전에는 어떤 문제가 있었는지 — 예: 요청 경로, 누락 사례, 몇 건 규모]** 그때 배운 게 권한은 사람이 아니라 역할에 묶어야 하고, 승인 단계와 실제 반영 단계가 따로 있어야 하고, 무엇보다 기록이 남아야 나중에 설명할 수 있다는 거였습니다. 이 프로젝트에 그걸 그대로 옮겼습니다. 권한을 역할 4개에 묶었고, 앱 검사와 DB 강제를 따로 뒀고, 모든 질문과 사용 문서, 거부된 접근을 감사 로그에 남겼습니다. AI가 사내 문서를 읽는다고 해서 권한 원칙이 달라지는 게 아니라, 오히려 한 번에 많은 문서를 읽으니까 더 엄격해야 한다고 생각합니다.

### Q5. 감사 로그에는 무엇을 남기고, AI 거버넌스와는 어떻게 연결되나요?

**답변 (30~45초)** — 사용자, 역할, 시각, 질문, 답변에 쓰인 문서 ID, 실행한 도구, 거부된 도구, 결과(답변, 모름, 오류)를 남깁니다. 답변 처리가 실패해도 기록은 남도록 별도 트랜잭션으로 썼습니다. 거버넌스 측면에서는 "누가 어떤 근거로 어떤 답을 받았는지" 추적할 수 있어야 문제가 생겼을 때 설명할 수 있고, 거부 기록이 갑자기 늘면 권한 설정 오류나 악용 시도를 의심할 수 있습니다. ISO/IEC 42001은 AI 경영시스템 표준이라 위험 관리와 투명성, 기록을 요구한다고 알고 있는데, 세부 조항까지 공부하진 못했고 개념 수준으로 이해하고 있습니다.

### 보너스 Q. 검색 결과가 이상할 때 어떻게 개선했나요?

**답변 (30~45초)** — 감으로 고치지 않고 수치로 봤습니다. 작업자가 근거 0건이길래 해당 질문과 공용 문서들의 거리를 재 보니 0.50에서 0.55로 기준 0.5를 살짝 넘고 있었고, 무관한 질문들은 0.58 이상이었습니다. 그래서 그 사이인 0.56으로 정했습니다. 또 정비원 답변에 관련 없는 경보 섹션이 섞여서, 벡터로 후보를 넉넉히 뽑은 뒤 경보 코드가 본문에 있으면 가산점을 주고 1등과 차이가 큰 건 버리는 재정렬을 넣었습니다. 바꿀 때마다 같은 질문을 4개 역할로 다시 보내서 전후를 비교했고, 마지막에는 자동 테스트로 고정했습니다.

## 05. 네트워크·보안·폐쇄망 — 입구 하나, 기본 거부, 인터넷 없이 설치

📘 노트: [05-network-security.md](study/05-network-security.md) · 개념서: [06-network-airgap.md](textbook/06-network-airgap.md)

### Q1. 쿠버네티스에서 외부 요청이 Pod까지 가는 경로를 설명해 주세요.

**답변 (30~45초)** — 제 구성 기준으로 말씀드리면, 브라우저가 https://localhost로 오면 노드의 443 포트에 hostPort로 붙어 있는 Traefik이 받습니다. Traefik이 TLS를 풀고, Ingress 규칙에서 경로가 /api면 ax-gateway 서비스로, 나머지는 web-ui 서비스로 보냅니다. 서비스는 고정 IP이고, 실제 Pod IP로 바꿔 주는 건 kube-proxy가 만든 규칙입니다. Pod끼리의 통신은 Calico가 깔아 준 네트워크로 가고, 서비스 이름을 IP로 바꾸는 건 CoreDNS입니다. 운영 환경이라면 Traefik 앞에 L4 로드밸런서가 하나 더 있다고 보시면 됩니다.

### Q2. NetworkPolicy를 어떻게 설계하고 어떻게 검증했나요?

**답변 (30~45초)** — 먼저 통신 지도를 그렸습니다. 채팅 화면은 게이트웨이로만, 게이트웨이는 LLM, 임베딩, DB로만, 수집 작업은 MinIO, 임베딩, DB로만 가면 됩니다. 그다음 네임스페이스 전체에 기본 거부를 걸고, DNS와 이 지도에 있는 통신만 허용했습니다. 게이트웨이는 MinIO를 안 써서 일부러 막았습니다. 검증은 실제 Pod 안에서 TCP 연결을 시도하는 스크립트로 했는데, 적용 전에는 14개 중 9개가 기대와 달리 열려 있었고 적용 후 14개 모두 기대대로 나왔습니다. 막고 나서 정상 기능이 깨지지 않았는지도 수집 작업과 권한 테스트로 바로 확인했습니다.

### Q3. 폐쇄망 고객사에 AI 플랫폼을 설치한다면 어떻게 하시겠어요?

**답변 (30~45초)** — 현장에서는 아무것도 인터넷에서 받지 않는다는 원칙으로 준비합니다. 사무실에서 이미지, 모델, 설치 매니페스트, 차트를 번들로 만들고 SHA256 체크섬을 남깁니다. 그리고 반입 전에 같은 번들로 인터넷을 막은 환경에서 설치 리허설을 합니다. 실제로 해 보니 번들 7.5기가로 15분 정도에 재구축됐고, 그 과정에서 멀티 아키텍처 이미지 저장 문제나 digest가 바뀌는 문제처럼 해 보기 전에는 몰랐던 문제를 다섯 개 찾았습니다. 현장에 내부 레지스트리가 있으면 이미지를 digest 그대로 push하는 게 정석이고, 반입 절차나 사내 CA, DNS, NTP는 사전에 고객과 협의해야 할 항목으로 체크리스트에 정리해 뒀습니다.

### Q4. GPU 클러스터의 네트워크는 어떻게 구성하나요? InfiniBand와 RoCE의 차이는요?

**답변 (30~45초)** — 보통 관리망, 서비스망, 스토리지망, GPU 연산망을 분리합니다. 학습에서는 GPU끼리 대량의 데이터를 계속 교환해서, 연산망을 400기가 이상으로 따로 두고 CPU를 거치지 않는 RDMA를 씁니다. InfiniBand는 전용 장비라 손실 없이 지연이 낮은 게 기본이고, RoCEv2는 이더넷 장비로 RDMA를 하는 방식이라 기존 이더넷 운영 경험을 살릴 수 있지만 손실 없는 설정을 잘 맞춰야 합니다. 구조는 Spine-Leaf로 서버 간 경로를 일정하게 하고요. 다만 이건 제가 공부로 이해한 수준이고 실제 스위치를 구성해 본 적은 없어서, 입사하면 가장 먼저 배우고 싶은 부분입니다.

### Q5. TLS 인증서는 어떻게 관리했나요? 만료되면 어떻게 되나요?

**답변 (30~45초)** — cert-manager로 사설 루트 CA를 만들고, 그 CA로 서버 인증서를 발급하게 했습니다. 서버 인증서는 90일짜리이고 만료 15일 전에 자동으로 갱신되게 설정했습니다. 인증서가 만료되면 브라우저와 클라이언트가 접속을 거부해서 서비스 전체가 멈춘 것처럼 보입니다. 실제 장애 원인으로 꽤 흔하다고 알고 있어서, 자동 갱신과 함께 만료 임박 알람도 걸어야 한다고 생각합니다. 고객사라면 보통 사내 CA가 이미 있으니 cert-manager의 발급자만 그쪽으로 바꾸면 됩니다.

### 보너스 Q. 오픈소스 컴포넌트가 지원 종료되면 어떻게 판단하나요?

**답변 (30~45초)** — 이번에 ingress-nginx를 쓰려다가 저장소가 2026년 3월에 보관 처리된 걸 확인했습니다. 은퇴한 컴포넌트를 새로 구축하면 보안 패치를 못 받으니 대안을 비교했는데요, Traefik은 기존 Ingress 방식 그대로라 빨리 적용할 수 있었고, Envoy Gateway는 차세대 표준인 Gateway API를 쓰지만 설정이 더 복잡했습니다. 일정과 고객사 현장 호환성을 기준으로 Traefik을 골랐고, 장기적으로는 Gateway API로 옮기는 게 맞다고 노트에 정리했습니다. 고객사에서 ingress-nginx를 쓰고 있다면 지원 종료 사실과 마이그레이션 계획을 먼저 알리는 게 기술지원 엔지니어의 역할이라고 생각합니다.

**꼬리 질문 키워드**: "NetworkPolicy가 라벨 기준이면, 누가 같은 라벨로 Pod를 만들면요?" / "kubectl port-forward는 NetworkPolicy에 막히나요?" / "폐쇄망에서 모델을 업데이트하려면?"


## 06. 모니터링·알람 — GPU·LLM·서비스를 한 화면에서

📘 노트: [06-observability.md](study/06-observability.md) · 개념서: [07-observability.md](textbook/07-observability.md)

### Q1. AI 서비스에서 무엇을 모니터링해야 하나요?

**답변 (30~45초)** — 4가지 황금 신호에 맞춰 나눴습니다. 지연은 첫 토큰까지 시간인 TTFT의 p95, 트래픽은 역할별 요청 수, 오류는 5xx 비율과 근거를 못 찾은 비율, 포화는 LLM 대기열과 GPU 사용률, 메모리, 온도입니다. 실제로 동시 요청을 6개 보내 봤더니 슬롯이 4개라 대기열이 생기고, 바로 TTFT p95가 1분까지 늘어나는 게 대시보드에 그대로 보였습니다. 그래서 TTFT 알람만 있으면 늦고, 대기열 알람이 앞단의 신호 역할을 한다고 판단했습니다.

### Q2. Prometheus는 어떻게 동작하나요? rate와 histogram_quantile은 왜 쓰나요?

**답변 (30~45초)** — Prometheus는 각 서비스의 /metrics를 15초마다 가져가서 저장하는 pull 방식입니다. 요청 수 같은 카운터는 계속 커지기만 해서 값 자체는 의미가 없고, rate로 초당 증가율을 봐야 합니다. 응답 시간은 히스토그램으로 구간별 개수를 모아 두고, histogram_quantile로 p95 같은 백분위를 계산합니다. 평균은 느린 소수 요청을 가려 버려서 사용자 체감은 p95로 보는 게 맞다고 생각합니다. 쿠버네티스에서는 ServiceMonitor라는 정의를 만들면 Operator가 수집 설정을 자동으로 만들어 줍니다.

### Q3. GPU 장애는 어떻게 감지하나요? Xid는 뭔가요?

**답변 (30~45초)** — NVIDIA DCGM exporter로 사용률, 메모리, 온도, 전력, Xid를 수집합니다. Xid는 드라이버가 보고하는 GPU 오류 번호인데, 79는 GPU가 PCIe 버스에서 떨어진 것, 48은 이중 비트 ECC로 메모리가 손상된 것이라 하드웨어 문제 가능성이 높고, 31은 메모리 페이지 폴트라 주로 애플리케이션 쪽 문제입니다. 제 PC에는 쿠버네티스에 붙은 GPU가 없어서 DCGM과 같은 지표 이름을 내는 시뮬레이터를 만들었고, 과열을 주입해서 85도 알람이 1분 뒤 critical로 울리는 것까지 확인했습니다. 지표 이름이 같아서 실제 서버에서는 exporter만 바꾸면 됩니다.

### Q4. 알람은 어떻게 설계하나요? 알람이 너무 많으면요?

**답변 (30~45초)** — 사람이 행동해야 하는 것만 걸고, 모든 알람에 심각도와 대응 문서 링크를 붙였습니다. critical은 즉시 대응, warning은 근무 시간 내 확인입니다. 일시적으로 튀는 값은 "1분 이상 지속" 같은 조건으로 거르고요. 알람이 많으면 다들 무시하게 되니까, 같은 원인의 알람은 Alertmanager에서 묶거나 억제하고, 오탐이 나는 건 바로 고쳐야 합니다. 실제로 Grafana 경로를 바꾸면서 생긴 TargetDown이나 kind에서 수집이 안 되는 구성요소 알람을 정리했습니다. 그리고 수집 배치가 깨졌던 경험이 있어서 Job 실패 알람을 추가했습니다.

### Q5. 대시보드를 만들 때 무엇을 기준으로 구성했나요?

**답변 (30~45초)** — 보는 사람이 다르다고 보고 두 개로 나눴습니다. 인프라 엔지니어용은 GPU 사용률, 온도, 메모리, Xid와 LLM 대기열, TTFT, 노드 자원이고, 서비스 운영용은 역할별 요청, 권한 거부, 근거 0건 비율, 5xx, DB 연결, 마지막 백업 시각입니다. 패널마다 알람 기준선을 같이 그려서 지금 얼마나 여유가 있는지 바로 보이게 했습니다. 대시보드는 코드로 생성해서 차트와 함께 배포되니까, 고객사에 설치할 때도 똑같이 들어갑니다.

**꼬리 질문 키워드**: "Prometheus 데이터는 얼마나 보관하나요?" / "모니터링 시스템이 죽으면요?" / "pull 방식이면 짧게 끝나는 배치 작업 지표는요?"


## 07. 백업과 복구 훈련 — "복구해 봐야 백업이다"

📘 노트: [07-backup.md](study/07-backup.md) · 개념서: [08-backup.md](textbook/08-backup.md)

### Q1. RPO와 RTO를 설명해 주시고, 직접 측정해 본 적 있나요?

**답변 (30~45초)** — RPO는 장애가 났을 때 얼마 전 데이터까지 잃어도 되는지이고, 백업 주기가 결정합니다. RTO는 서비스를 얼마 만에 되살려야 하는지이고요. 직접 측정해 봤는데, 백업 직후에 데이터를 하나 더 넣고 문서 테이블을 실제로 지운 다음 최신 백업으로 복구했습니다. 장애부터 기능 확인까지 48초가 걸렸고, 백업부터 장애까지 36초 동안 넣은 데이터는 실제로 사라졌습니다. 데이터가 500KB 정도라 빨랐던 거고, 실제 고객 규모라면 덤프 크기와 인덱스 재생성 시간 때문에 훨씬 길어지니까 그 규모로 다시 재 봐야 한다고 생각합니다.

### Q2. 복제나 RAID가 있으면 백업이 필요 없지 않나요?

**답변 (30~45초)** — 아니라고 생각합니다. 복제와 RAID는 하드웨어 고장에 대비한 거라, 누가 실수로 테이블을 지우거나 랜섬웨어가 데이터를 암호화하면 그것도 그대로 복제됩니다. 백업은 과거 시점으로 되돌릴 수 있는 별도 사본이라 목적이 다릅니다. 그래서 운영에서는 둘 다 두고, 백업은 3-2-1 원칙으로 다른 장소에도 하나 두는 게 기본이라고 알고 있습니다.

### Q3. 랜섬웨어에 대비한 백업은 어떻게 해야 하나요?

**답변 (30~45초)** — 랜섬웨어는 운영 서버뿐 아니라 백업 서버까지 찾아서 지우거나 암호화하는 경우가 많아서, 정해진 기간 동안 관리자도 지울 수 없는 불변 백업이 핵심입니다. MinIO의 Object Lock, 엑사그리드의 시간 잠금 계층, Veeam의 Hardened Repository가 그런 기능으로 알고 있습니다. 그리고 백업 저장소의 계정을 운영 계정과 분리하고, 오프사이트 사본을 두고, 정기적으로 복구 훈련을 해서 실제로 되살아나는지 확인해야 합니다. 제 프로젝트는 일반 버킷에 저장해서 불변 설정까지는 못 했고, 그 부분을 후속 과제로 적어 뒀습니다.

### Q4. 쿠버네티스 환경에서는 무엇을 백업해야 하나요?

**답변 (30~45초)** — 크게 세 가지라고 봅니다. 첫째, 상태 데이터인 DB와 오브젝트 스토리지, 볼륨입니다. 둘째, 쿠버네티스 리소스 정의인데, 이건 git에 차트와 값으로 있으면 거기서 재현할 수 있습니다. 셋째, Secret처럼 git에 둘 수 없는 것들은 별도 비밀 관리 도구가 원본이 돼야 합니다. 저는 DB는 pg_dump로 MinIO에 매일, 설정은 Helm 값과 매니페스트를 내보냈고, Secret 값은 평문 유출 위험 때문에 일부러 빼고 목록만 남겼습니다. 운영이라면 Velero 같은 도구로 리소스와 볼륨 스냅샷을 함께 백업하는 걸 검토하겠습니다.

### Q5. 백업이 실패하면 어떻게 알 수 있나요?

**답변 (30~45초)** — 백업 CronJob의 마지막 성공 시각을 지표로 보고, 24시간 넘게 성공이 없으면 critical 알람이 울리게 했습니다. 실제로 백업 직후에 "마지막 성공 후 82초"로 잡히는 걸 확인했고요. 실패 자체를 잡는 Job 실패 알람도 따로 있습니다. 백업은 조용히 실패하는 게 제일 위험하다고 생각해서, 성공했다는 신호가 끊기는 걸 감시하는 방식으로 만들었습니다.

**꼬리 질문 키워드**: "pg_dump를 슈퍼유저로 한 이유는?" / "벡터DB는 원본 문서로 다시 만들 수 있는데 백업해야 하나요?" / "백업 파일이 손상됐는지는 어떻게 알아요?"


## 08. 장애 대응 — 증상에서 근본 원인까지

📘 노트: [08-troubleshooting.md](study/08-troubleshooting.md) · 개념서: [09-troubleshooting.md](textbook/09-troubleshooting.md)

### Q1. 고객이 "AI가 답을 안 해요"라고 하면 어떻게 대응하시겠어요?

**답변 (30~45초)** — 먼저 증상을 구체화합니다. 로그인이나 화면은 되는지, 언제부터인지, 전원이 안 되는지 일부만 안 되는지요. 그다음 요청 경로인 입구, 게이트웨이, 임베딩, DB, LLM 순으로 Pod 상태를 보고, 이상한 Pod가 있으면 describe의 Last State와 Events, 로그를 봅니다. 마지막으로 그 시점에 무엇이 바뀌었는지 배포 이력과 맞춰 봅니다. 실제로 훈련할 때 처음에 오래전부터 있던 다른 Job 오류를 원인으로 잘못 짚었는데, 시점과 경로가 맞지 않는다는 걸 확인하고 LLM Pod의 OOMKilled를 찾았습니다. 그 경험 이후로 "언제부터, 어느 경로"를 꼭 같이 봅니다.

### Q2. Exit Code 137, 1, 143은 각각 무엇인가요?

**답변 (30~45초)** — 137은 128 더하기 9라서 SIGKILL로 강제 종료된 거고, 쿠버네티스에서는 대부분 메모리 limit 초과로 커널이 죽인 OOMKilled입니다. 1은 애플리케이션이 오류로 스스로 종료한 경우라 로그를 봐야 하고요. 143은 128 더하기 15, SIGTERM이라 정상적인 종료 요청을 받은 겁니다. 배포나 스케일 다운 때 흔히 봅니다. 저는 LLM 메모리 limit을 모델보다 작게 줄인 장애에서 OOMKilled에 137을 직접 확인했습니다. 반대로 CPU limit 초과는 죽지 않고 느려지기만 해서, Grafana가 응답이 없을 때 kubectl top으로 throttling을 찾은 적도 있습니다.

### Q3. Pod가 Running인데 서비스가 안 됩니다. 무엇을 의심하나요?

**답변 (30~45초)** — READY 열을 봅니다. Running인데 0/1이면 프로세스는 살아 있지만 준비 검사에 실패해서 Service가 트래픽을 보내지 않는 상태입니다. 모델 업그레이드 장애 훈련에서 정확히 이랬는데, Events에 "모델을 찾을 수 없다"는 readiness 실패 메시지가 있었습니다. 배포 도구는 성공으로 나왔지만, 그건 설정이 클러스터에 들어갔다는 뜻이지 앱이 준비됐다는 뜻이 아니어서, 배포할 때 wait와 자동 롤백을 써야 한다고 정리했습니다.

### Q4. 보안 사고가 의심될 때는 어떻게 조사하고 보고하나요?

**답변 (30~45초)** — 세 가지를 순서대로 답하려고 합니다. 무엇이 바뀌었는지, 실제로 피해가 있었는지, 누가 무엇을 했는지요. 권한 필터가 꺼진 배포를 조사할 때 먼저 설정에서 필터 비활성화를 확인했고, 감사 로그에서 작업자 계정이 품질 문서를 노린 질문을 한 기록을 찾았는데 사용된 문서가 0건이었습니다. 왜 막혔는지도 DB에 직접 같은 조건으로 조회해서, 행 수준 보안이 작업자에게 품질 문서를 0건으로 보여 주는 걸 증명했습니다. 보고서에는 타임라인, 영향 범위, 근본 원인, 임시·영구 조치와 고객 공유 문구를 넣었고, "유출 없음"을 추측이 아니라 감사 로그와 DB 검증으로 말할 수 있게 했습니다.

### Q5. 장애 재발을 막으려면 무엇을 해야 하나요?

**답변 (30~45초)** — 사람을 탓하기보다 구조를 고쳐야 한다고 생각합니다. 이번에 찾은 원인들은 모두 배포 변경이었는데요, 메모리 축소, 없는 모델 이름, 과도한 GPU 요청, 보안 설정 비활성화였습니다. 그래서 배포할 때 준비 실패 시 자동 롤백, 권한 자동 테스트 필수화, 보안 설정 값 정책 검사, 그리고 재시작이나 권한 거부 급증 알람을 재발 방지책으로 정했습니다. 저도 원복 스크립트가 이전 값을 다시 적용하는 실수를 했는데, 원복 후 실제 값을 검증하도록 고쳤습니다. 확인 단계를 자동화하는 게 제일 확실하다고 봅니다.

## 09. 사이징과 기술 제안 — 요구사항을 GPU 대수로 바꾸기

📘 노트: [09-sizing.md](study/09-sizing.md) · 개념서: [10-sizing.md](textbook/10-sizing.md)

### Q1. 고객이 "직원 800명이 쓸 AI를 만들고 싶은데 GPU가 몇 장 필요하냐"고 묻는다면?

**답변 (30~45초)** — 바로 숫자를 드리기보다 먼저 몇 가지를 여쭙겠습니다. 동시에 쓰는 사람이 몇 명인지, 주로 짧은 질문인지 긴 문서 요약인지, 응답 속도를 어느 정도 기대하시는지, 폐쇄망인지요. 그걸로 동시 생성 요청 수와 컨텍스트 길이를 정하고, 가중치 더하기 KV 캐시 더하기 여유분으로 메모리를 계산합니다. 가상 RFP로 해 보면 동시 100명을 동시 요청 30건으로 보고 32B 모델을 FP8로 올리면 약 71GB라 L40S 2장에 1벌이 들어가서, 이중화를 위해 4장짜리 서버 2대를 제안했습니다. 다만 이건 근사치라 PoC에서 실제 질문으로 측정해 확정하겠다고 말씀드리겠습니다.

### Q2. KV 캐시가 왜 중요한가요?

**답변 (30~45초)** — KV 캐시는 모델이 앞에서 읽은 내용을 다시 계산하지 않으려고 저장해 두는 메모리인데, 컨텍스트 길이와 동시 요청 수에 비례해서 커집니다. 계산해 보니 32B FP8 모델에서 가중치가 32GB인데 동시 30건, 4천 토큰이면 KV 캐시도 32GB였습니다. 즉 모델이 GPU에 들어간다고 끝이 아니고, 사용자가 늘면 KV 캐시 때문에 GPU가 모자라게 됩니다. 그래서 RAG처럼 근거 문서를 길게 넣는 서비스는 컨텍스트 관리와 동시성 설계가 GPU 비용을 좌우한다고 봅니다.

### Q3. L40S, H100, H200은 어떻게 고르나요?

**답변 (30~45초)** — 추론 위주에 7~14B 모델이면 L40S로도 충분한 경우가 많고, PCIe라 서버 구성이 유연합니다. 30B급 이상이나 텐서 병렬이 필요하면 NVLink가 있는 H100이 유리하고, 긴 컨텍스트나 동시 사용자가 많아 KV 캐시가 크면 메모리가 141GB인 H200이 좋습니다. A100은 FP8을 지원하지 않아서 FP8 양자화 모델을 쓰려면 고려해야 합니다. 학습까지 한다면 GPU 간 고속 통신이 핵심이라 기준이 완전히 달라집니다. 제 계산기에서도 GPU별로 필요한 장수와 이런 주의점을 같이 표시하게 했습니다.

### Q4. 온프레미스와 클라우드 LLM API 중 무엇을 권하시겠어요?

**답변 (30~45초)** — 고객 조건에 따라 다릅니다. 폐쇄망이 필수거나 문서를 외부로 보낼 수 없으면 온프레미스가 사실상 유일한 선택지입니다. 비용은 초기 투자가 크지만 사용량이 많을수록 유리하고, 클라우드 API는 초기 부담이 적은 대신 사용량에 비례해 늘어납니다. 운영 인력이 적으면 클라우드가 편하지만, 온프레미스도 자동 감시와 런북, 기술지원 계약으로 보완할 수 있습니다. 이번 가상 RFP는 폐쇄망 조건이라 온프레미스로 제안했습니다.

### Q5. PoC는 어떻게 설계하나요?

**답변 (30~45초)** — 성공 기준을 숫자로 먼저 고객과 합의합니다. 예를 들어 현업과 만든 질문 100개에서 근거 문서 적중 80% 이상, 권한 밖 문서 노출 0건, 동시 30건에서 첫 응답 p95 3초 이내, 폐쇄망 재구축 하루 이내, 복구 1시간 이내 같은 식입니다. 그리고 모델 크기나 양자화를 바꿔 가며 같은 질문 세트로 비교해서 품질, 속도, GPU 수의 트레이드오프를 표로 보여 드리고 결정하시게 합니다. 제 프로젝트에서도 권한 테스트, 폐쇄망 리허설, 복구 훈련을 수치로 남겼는데, PoC 성공 기준을 그 방식으로 만들었습니다.
