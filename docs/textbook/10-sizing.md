# 10장. 사이징과 기술 제안

> 관련: M9 · 노트 [09-sizing](../study/09-sizing.md) · [가상 RFP 제안서](../proposal-sample.md) · 계산기 `apps/sizing`

## 10.1 사이징이란: 요구사항을 장비로 번역하기

**정의**: 고객의 요구사항(사용자 수, 데이터 양, 응답 속도, 보안 조건)을 장비 규모(GPU 종류·수, 메모리, 스토리지, 네트워크)로 바꾸는 계산과 판단이다.

**3단계**
1. **정량화**: "100명이 쓴다" → "동시 생성 요청 30건, 요청당 4,096토큰". 가정(활성 비율 30%)을 **명시**한다.
2. **계산**: 공식으로 메모리·용량을 구한다(10.2~10.4).
3. **판단**: 이중화, 확장 여유, 폐쇄망, 운영 인력 같은 **비계산 요소**로 구성을 정하고, PoC로 확정한다.

**흔한 오해**: "정확한 숫자를 주는 게 사이징이다" → 사이징은 근사치다. 고객이 사는 건 숫자 하나가 아니라 **"왜 이 구성인가"의 근거**다.

## 10.2 LLM GPU 메모리 공식

```
GPU 메모리 ≈ 가중치 + KV 캐시 + 여유분

가중치   = 파라미터 수 × 바이트 (FP16 2 / FP8·INT8 1 / INT4 0.5)
KV 캐시  = 2 × 레이어 × KV헤드 × 헤드차원 × 2바이트 × 컨텍스트 × 동시 요청
여유분   = (가중치 + KV) × 약 10%   (활성값, CUDA 컨텍스트, 단편화)
GPU 가용 = 용량 × 약 90%            (vLLM gpu_memory_utilization 관례)
```

**계산 예 (M9 가상 RFP)**: 32B FP8, 동시 30건, 4,096토큰, 64레이어·KV헤드 8·헤드차원 128
- 가중치 = 32 × 1 = **32.0GB**
- KV = 2 × 64 × 8 × 128 × 2B × 4,096 × 30 ≈ **32.2GB**
- 여유 = 6.4GB → **합계 70.6GB**
- L40S(48GB, 가용 43.2) → **2장 텐서 병렬** / H100(80GB, 가용 72) → 1장(여유 거의 없음) / H200(141GB) → 1장 넉넉

**핵심 통찰**: KV 캐시가 가중치만큼 컸다. **GPU 대수는 모델 크기보다 동시성과 컨텍스트가 결정한다.** 동시 요청이 2배면 KV도 2배다.

**면접 한 줄**: "GPU 메모리는 가중치, KV 캐시, 여유분의 합이고, 동시 사용자가 늘면 KV 캐시 때문에 모델이 들어가도 GPU가 모자랄 수 있습니다."

## 10.3 텐서 병렬과 레플리카

| | 텐서 병렬 (TP) | 레플리카 |
|---|---|---|
| 정의 | 모델 **한 벌을 여러 GPU에 쪼개** 올림 | 모델을 **여러 벌** 띄움 |
| 해결하는 문제 | 한 GPU에 모델이 안 들어감 | 처리량 부족, 고가용성 |
| 조건 | GPU 간 통신이 매우 많음 → **같은 서버 안**, NVLink가 유리(PCIe는 병목 가능) | 서버를 나눠도 됨 |
| 크기 | 보통 2의 거듭제곱(1, 2, 4, 8) | 필요한 만큼 |

**파이프라인 병렬**(레이어를 나눠 여러 서버에)은 초대형 모델·학습에서 쓴다.

**M9 제안 구성**: L40S 4장 서버 2대 → 서버마다 LLM 1벌(TP2) → **한 대가 고장 나도 서비스 유지**, 남는 GPU로 임베딩·에이전트·비전 AI.

**면접 한 줄**: "모델이 한 GPU에 안 들어가면 텐서 병렬로 쪼개고, 처리량과 가용성은 레플리카로 늘립니다."

## 10.4 벡터DB·운영 데이터 용량

```
청크 수   = 문서 수 × ⌈쪽수 × 쪽당 글자 ÷ (청크 크기 − 겹침)⌉
벡터      = 청크 × 차원 × 4바이트
HNSW      ≈ 벡터 + 청크 × m × 2 × 8바이트 (이웃 링크)
본문      = 청크 × 청크 글자 × 3바이트 (한글 UTF-8)
감사 로그 = 일 질의 × 365 × 행 크기(약 1.5KB) × 보관 연수
백업      = (DB + 감사 로그) × 압축률 × 보관 개수
```
**예**: 문서 2만 건 × 10쪽 → 청크 50만 → 벡터 2.05 + 인덱스 2.18 + 본문 1.05 = **약 5.3GB**. 이 규모는 pgvector로 충분하고, HNSW를 메모리에 상주시킬 DB 메모리를 확보한다. 최초 임베딩은 CPU 실측 속도로 약 63시간 → GPU 임베딩 필요.

## 10.5 GPU 선택 기준

| GPU | 메모리 | 특징 | 적합 |
|---|---|---|---|
| **L40S** | 48GB GDDR6 | Ada, FP8 지원, PCIe, 추론·그래픽 겸용 | 7~32B 추론, 비전, 서버 구성 유연 |
| **A100** | 40/80GB HBM2e | Ampere, **FP8 미지원**, NVLink, MIG | 기존 자산, INT8·FP16 |
| **H100** | 80GB HBM3 | Hopper, FP8, NVLink, MIG | 30~70B 추론, 학습 |
| **H200** | 141GB HBM3e | H100 + 대용량·고대역 메모리 | 긴 컨텍스트, 많은 동시 사용자, 70B+ |

**학습 vs 추론**: 학습은 가중치 외에 그래디언트·옵티마이저 상태(가중치의 수 배 메모리)와 GPU 간 고속 통신(NVLink, InfiniBand)이 핵심이다. 추론은 메모리 용량·대역폭과 지연이 핵심이다. 사이징 방식이 완전히 다르다.

**비계산 요소**: 랙당 전력·냉각(GPU 서버는 대당 수 kW), 상면, 조달 리드타임, 벤더 지원, 기존 인프라.

## 10.6 온프레미스 vs 클라우드 LLM API

| 기준 | 온프레미스 GPU | 클라우드 LLM API |
|---|---|---|
| 보안·망분리 | 데이터가 사내에 머무름, **폐쇄망 가능** | 외부 전송 필요 |
| 비용 구조 | CAPEX + 전력·운영, **사용량이 많을수록 유리** | OPEX, 사용량 비례, 초기 부담 낮음 |
| 확장성 | 조달 기간 필요 | 즉시 |
| 모델 | 공개 모델(sLLM), 직접 튜닝 | 최신 대형 모델 |
| 운영 | GPU·쿠버네티스·모델 운영 역량 필요 | 운영 부담 낮음 |

**TCO(총소유비용)**: 장비 구매 + 전력·냉각 + 상면 + 운영 인력 + 유지보수. 사용량이 일정 수준을 넘으면 온프레미스가 유리해지는 손익분기점이 있다(구체 수치는 고객 조건마다 다름).

## 10.7 PoC 설계

**원칙**: 시작 전에 **성공 기준을 숫자로 합의**한다. "좋아 보인다"로 끝나는 PoC는 의사결정에 쓸 수 없다.

**M9 제안서의 기준 예**
| 항목 | 기준 |
|---|---|
| 답변 품질 | 질문 100개에서 근거 문서 적중 80% 이상, 근거 없는 질문 "모름" 90% 이상 |
| 권한 | 권한 밖 문서 노출 0건 |
| 성능 | 동시 30건에서 TTFT p95 3초 이내, 오류율 1% 미만 |
| 폐쇄망 | 반입 번들로 1일 이내 재구축 |
| 복구 | RTO 1시간 이내 |
| 모델 선택 | 14B vs 32B, FP8 vs INT4를 같은 질문 세트로 비교 |

## 10.8 고객에게 설명하기

**요구사항 정량화 질문**: 총·동시 사용자와 피크 시간, 주 시나리오(짧은 Q&A / 긴 요약), 응답 속도 기대, 문서 건수·형식·갱신 주기·권한 체계, 폐쇄망·반입 절차·로그 보관, 가용성(RTO/RPO), 확장 계획, 운영 인력, 상면·전력.

**비전공 고객에게**: 용어 대신 영향으로 말한다.
- "GPU 2장이 AI 한 세트를 맡고, 서버 2대에 한 세트씩 두어 한 대가 고장 나도 계속 쓸 수 있습니다."
- "동시에 질문하는 분이 두 배가 되면 GPU 메모리도 거의 두 배 필요합니다."
- "이 숫자는 계산으로 뽑은 근사치라, 시범 운영에서 실제 질문으로 확인하고 확정하겠습니다."

**면접 한 줄**: "사이징은 요구사항을 가정과 함께 정량화하고, 공식으로 계산하고, 이중화·확장·폐쇄망 같은 판단을 더한 뒤 PoC로 확정하는 과정입니다."
