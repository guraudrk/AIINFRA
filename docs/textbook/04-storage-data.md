# 4장. 스토리지, 데이터베이스, 벡터 검색

> 관련: M3 데이터 계층 · 노트 [03-data-layer](../study/03-data-layer.md)

## 4.1 블록·파일·오브젝트 스토리지

| | 블록 | 파일 | 오브젝트 |
|---|---|---|---|
| **정의** | 디스크를 일정 크기 블록으로 쪼개 OS에 "빈 디스크"로 붙임 | 폴더·파일 구조를 여러 서버가 네트워크로 공유 | 파일을 객체(데이터 + 메타데이터)로 통째로 저장하고 키로 접근 |
| **접근 방식** | OS가 파일시스템을 직접 만들어 씀 | NFS, SMB | HTTP API (S3) |
| **강점** | 빠른 랜덤 읽기·쓰기, 낮은 지연 | 여러 서버가 동시에 같은 파일 사용 | 거의 무한 확장, 저렴, 메타데이터·버전·잠금 |
| **약점** | 보통 한 서버만 붙음 | 대규모에서 메타데이터 병목 | 부분 수정 불가(통째로 다시 씀), 지연이 큼 |
| **대표** | SAN, iSCSI, 클라우드 디스크(EBS) | NAS, Dell PowerScale, NetApp | Amazon S3, **MinIO**, Dell ECS |
| **AI 플랫폼 용도** | DB(PostgreSQL), etcd | 학습 데이터 공유, 체크포인트 | **원본 문서, 모델 파일, 백업** |

**동작 원리 — 왜 DB는 블록에 두나**: DB는 작은 페이지(PostgreSQL 8KB)를 무작위로 읽고 쓰며, 쓰기가 디스크에 확실히 기록됐는지(fsync)가 중요하다. 블록 스토리지는 이걸 가장 빠르고 예측 가능하게 해 준다. 반면 원본 문서는 한 번 쓰고 통째로 읽으니 오브젝트가 맞다.

**이 프로젝트에서는**: 원본 문서·CSV·백업은 MinIO(S3 호환), 검색용 청크·벡터·정형 데이터는 PostgreSQL(블록, PVC). 원본이 따로 있어서 청크 전략이나 임베딩 모델을 바꿀 때 언제든 다시 만들 수 있다.

**면접 한 줄**: "DB처럼 랜덤 읽기·쓰기가 많은 건 블록, 여러 서버가 공유하는 건 파일, 원본·백업·모델처럼 통째로 쌓는 건 오브젝트 스토리지를 씁니다."

## 4.2 S3 API와 MinIO

**정의**: S3는 아마존의 오브젝트 스토리지이고, 그 API(버킷 생성, 객체 업로드·다운로드·목록)가 업계 표준이 됐다. MinIO는 같은 API를 쓰는 **설치형** 오브젝트 스토리지다.

**동작 원리**
- **버킷**(최상위 보관 단위) 안에 **키**(`docs/MAN-PRESS-03.md` 같은 경로형 이름)로 객체를 저장한다. 폴더처럼 보이지만 실제로는 키 이름에 `/`가 들어 있을 뿐이다.
- **분산 모드**: MinIO는 4대 이상 서버에 데이터를 **이레이저 코딩**(데이터를 조각내고 패리티를 추가)으로 나눠 저장해서, 일부 디스크나 서버가 고장 나도 읽을 수 있다.
- **Object Lock (WORM)**: 정해진 기간 동안 객체를 지우거나 바꿀 수 없게 잠근다 → 랜섬웨어 대비 불변 백업(8장).

**이 프로젝트에서는**: boto3(아마존용 파이썬 SDK)로 MinIO에 업로드·다운로드했다. **S3 호환이라 코드 수정 없이 동작**한다. 커뮤니티 공식 이미지 배포가 중단돼(Docker Hub 404) 소스 빌드 이미지(Chainguard)를 digest로 고정했다.

**실무 포인트**: 기업 고객은 기술 지원과 보안 패치가 있는 상용판(MinIO AIStor)을 쓰는 게 일반적이고, 에티버스가 MinIO 총판이다.

**면접 한 줄**: "MinIO는 S3 API를 그대로 쓰는 설치형 오브젝트 스토리지라 클라우드용 코드를 폐쇄망 안에서도 그대로 쓸 수 있습니다."

## 4.3 쿠버네티스 저장소: PV, PVC, StorageClass, CSI

**정의**
- **PV(PersistentVolume)**: 실제 디스크 한 덩어리
- **PVC(PersistentVolumeClaim)**: Pod가 "디스크 10GB 주세요"라고 내는 요청서
- **StorageClass**: PVC가 오면 어떤 디스크를 어떻게 만들지 정한 규칙(동적 프로비저닝)
- **CSI**: 외부 스토리지(Dell, NetApp, Ceph)를 쿠버네티스에 붙이는 표준 플러그인 규격

**동작 원리**
1. Pod가 PVC를 쓰겠다고 선언한다.
2. StorageClass의 프로비저너가 PV를 만들어 PVC와 묶는다(Bound).
3. `volumeBindingMode: WaitForFirstConsumer`면 **Pod가 갈 노드가 정해진 뒤** 그 노드에 디스크를 만든다. 로컬 디스크에서는 디스크와 Pod가 다른 노드에 생기는 문제를 막는다.
4. **접근 모드**: RWO(한 노드에서만 읽기·쓰기), RWX(여러 노드에서 동시), ROX(읽기 전용 다중).

**이 프로젝트에서는**: kind 기본 StorageClass `standard`(local-path, 노드 로컬 디스크, WaitForFirstConsumer). M2에서 Pod가 잠깐 Pending이었다가 PVC가 만들어지자 GPU 노드에 배정되는 순서를 확인했다. 단점으로 local-path는 kubelet이 사용량을 보고하지 않아 **PVC 사용률 지표가 비었다**(M6).

**흔한 오해**: "PVC가 있으면 데이터가 안전하다" → 노드 로컬 디스크는 노드가 죽으면 같이 사라진다. 운영은 외부 스토리지(CSI) + 백업이다.

**면접 한 줄**: "PVC는 디스크 요청서이고 StorageClass가 실제 디스크를 만들어 주며, 외부 스토리지는 CSI 드라이버로 붙입니다."

## 4.4 PostgreSQL 핵심: 트랜잭션, 역할과 권한

**트랜잭션**: 여러 작업을 "**전부 성공 아니면 전부 취소**"로 묶는다(ACID의 A, 원자성).
- 이 프로젝트에서 정형 데이터 적재를 `TRUNCATE + 7개 테이블 적재`로 한 트랜잭션에 묶었다. M4 이후 RLS 때문에 COPY가 실패했을 때 **TRUNCATE까지 롤백되어 데이터가 비지 않았다.**
- 복구도 `pg_restore --single-transaction`으로 반쯤 복구된 상태가 남지 않게 했다.

**역할(Role)과 최소 권한**
| 역할 | 권한 | 이유 |
|---|---|---|
| postgres | 슈퍼유저 | 관리·백업 전용 |
| ax_ingest | 문서·정형 테이블 쓰기 | 수집 파이프라인 |
| ax_app | 읽기 + 감사 로그 쓰기, **RLS 대상** | 사내 AI 앱 |
| ax_monitor | pg_monitor (통계 뷰만) | 모니터링 |

- `GRANT`로 권한을 준다. **TRUNCATE는 DELETE와 별도 권한**이라 빠뜨렸다가 수집이 실패했다(M3).

**면접 한 줄**: "계정을 용도별로 나눠 최소 권한만 주고, 여러 단계의 적재나 복구는 트랜잭션으로 묶어 실패 시 원래 상태로 돌아가게 했습니다."

## 4.5 벡터 검색과 pgvector

**정의**: 벡터 검색은 질문 벡터와 가장 가까운 문서 벡터를 찾는 것이다. pgvector는 PostgreSQL에 벡터 타입(`vector(1024)`)과 거리 연산자, 인덱스를 추가하는 확장이다.

**거리 척도**
- **코사인 거리** `<=>`: 1 − 코사인 유사도. 방향이 같을수록 0에 가깝다. 문장 임베딩에서 가장 많이 쓴다.
- 유클리드 `<->`, 내적 `<#>`.

**인덱스 — 정확한 검색 vs 근사 검색**
- 인덱스 없이: 모든 벡터와 비교(정확하지만 N에 비례해 느림). 수천 개면 충분.
- **HNSW**: 벡터들을 여러 층의 "이웃 그래프"로 연결하고, 위층(듬성듬성)에서 아래층(촘촘)으로 내려가며 가까운 이웃을 찾는다. 빠르고 정확도가 높지만 **메모리를 많이 쓰고**, 빌드가 느리다. 파라미터 `m`(이웃 수), `ef_search`(탐색 폭).
- **IVFFlat**: 벡터를 군집으로 나누고 가까운 군집만 탐색한다. 빌드가 빠르고 메모리가 적다.
- **필터 + 근사 검색 문제**: HNSW가 후보를 뽑은 뒤 WHERE 조건(권한 등급)으로 거르면 결과가 모자랄 수 있다. pgvector 0.8의 `hnsw.iterative_scan`이 부족하면 더 탐색한다(이 프로젝트에서 켬).

**용량 공식**: 청크 수 × 차원 × 4바이트(float32) + 인덱스 + 본문. 이 프로젝트 138청크 × 1024 × 4B ≈ 0.56MB(벡터만), 실제 테이블 2.0MB, HNSW 1.1MB. 문서 2만 건(청크 50만)이면 약 5.3GB(M9).

**면접 한 줄**: "pgvector는 PostgreSQL에서 벡터를 저장하고 코사인 거리로 가까운 것을 찾게 해 주고, 규모가 커지면 HNSW 근사 인덱스를 씁니다."

## 4.6 청크(Chunking) 전략

**정의**: 긴 문서를 검색과 LLM 입력에 적당한 크기로 자르는 것이다.

**왜 필요한가**
1. LLM 컨텍스트에 문서 전체를 넣을 수 없다(3장).
2. 관련 없는 내용이 섞이면 답이 흐려진다.
3. 임베딩은 한 덩어리를 하나의 벡터로 요약하므로, 너무 길면 의미가 희석된다.

**설계 선택**
| 선택 | 이 프로젝트 | 이유 |
|---|---|---|
| 자르는 단위 | **제목(##, ###) 단위** | 경보 코드 하나의 원인·조치·부품이 한 조각에 함께 |
| 최대 크기 | 700자 | 한 섹션이 대부분 들어가는 크기 |
| 겹침 | 100자 | 경계에 걸친 문장이 양쪽 조각에 남게 |
| 맥락 머리말 | `[문서 제목 > 섹션]` | 조각만 봐도 어떤 설비의 무엇인지 알 수 있게 |

**흔한 오해**: "작게 자를수록 정확하다" → 너무 작으면 원인과 조치가 다른 조각으로 찢어져 답에 필요한 맥락을 잃는다.

**면접 한 줄**: "문서 구조(제목) 단위로 잘라 의미 단위를 지키고, 길면 겹침을 두어 나누고, 조각마다 문서·섹션 맥락을 붙였습니다."

## 4.7 온톨로지(관계 데이터)와 하이브리드 검색

**정의**: 온톨로지는 개념 사이의 관계를 정의한 것이다. 이 프로젝트에서는 **설비 ↔ 경보 코드 ↔ 부품 ↔ 문서** 관계 테이블(alarm_parts, alarm_documents)로 가볍게 구현했다.

**왜 필요한가**: "3호기 E-203에 필요한 부품과 재고"처럼 **정확한 관계**는 벡터 검색(비슷한 것 찾기)으로 답할 수 없다. SQL 조인으로 정확히 답한다. 또 "3호기"만 있는 질문에서 E-203이 프레스에만 있다는 관계로 설비 종류를 판단했다(M4).

**하이브리드 검색**: 의미(벡터) 검색과 키워드(정확 일치) 검색을 섞는다. M3에서 "E-203"만 검색하자 거의 같은 내용인 4호기 매뉴얼이 3호기보다 위에 나왔다. 그래서 M4에서 ① 설비 ID를 메타데이터 필터로 걸고 ② 경보 코드가 본문에 있으면 가산점을 주는 재정렬을 넣었다.

**면접 한 줄**: "벡터 검색은 비슷한 걸 찾는 데 강하고 정확한 관계에는 약해서, 설비·경보·부품 관계는 테이블로 두고 메타데이터 필터와 키워드 재정렬을 섞었습니다."
