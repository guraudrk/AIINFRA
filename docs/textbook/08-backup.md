# 8장. 백업과 복구

> 관련: M7 · 노트 [07-backup](../study/07-backup.md) · [복구 훈련 보고서](../restore-drill-report.md)

## 8.1 백업, 복제, RAID는 다르다

| | 목적 | 막는 것 | 못 막는 것 |
|---|---|---|---|
| **RAID** | 디스크 여러 개를 묶어 디스크 고장 대비 | 디스크 1~2개 고장 | 서버 고장, 실수 삭제, 랜섬웨어 |
| **복제 (Replication)** | 다른 서버에 실시간 사본 | 서버 고장(장애 전환) | **실수 삭제·암호화도 그대로 복제** |
| **백업** | 특정 시점 사본을 따로 보관 | 실수 삭제, 랜섬웨어, 논리 오류 | 백업 이후 변경분(→ RPO) |

**핵심**: 복제와 RAID는 **가용성**, 백업은 **시점 복구**다. 둘 다 필요하다.

**면접 한 줄**: "복제와 RAID는 하드웨어 고장에 대비한 것이고, 실수 삭제나 랜섬웨어처럼 데이터 자체가 망가진 경우는 과거 시점 사본인 백업으로만 되돌릴 수 있습니다."

## 8.2 RPO와 RTO

**정의**
- **RPO (Recovery Point Objective)**: 장애 시 **최대 얼마 전 시점까지의 데이터를 잃어도 되나**. 백업 주기가 결정한다.
- **RTO (Recovery Time Objective)**: 장애 후 **얼마 만에 서비스를 되살려야 하나**. 복구 절차·데이터 크기·사람의 숙련도가 결정한다.

```
      마지막 백업            장애 발생                     서비스 정상화
 ────────●──────────────────────●──────────────────────────────●──────▶ 시간
         │◀──── RPO(잃는 구간) ──▶│◀────────── RTO(중단 시간) ────▶│
```

**이 프로젝트 실측**: 백업 → 20초 뒤 데이터 1건 추가 → 장애(테이블 삭제) → 복구. **RTO 48초, RPO 36초**, 추가했던 1건은 실제로 사라짐.

**줄이는 방법**: RPO는 백업 주기 단축, **WAL 아카이빙(PITR)**, 복제. RTO는 자동화된 복구 스크립트, 작은 복구 단위, 정기 훈련, 대기 시스템.

**면접 한 줄**: "RPO는 잃어도 되는 데이터 범위로 백업 주기가 정하고, RTO는 복구에 걸리는 시간으로 실제로 해 봐야 압니다. 저는 훈련으로 RTO 48초, RPO 36초를 측정했습니다."

## 8.3 백업 방식: 논리, 물리, PITR

| 방식 | 도구 | 장점 | 단점 |
|---|---|---|---|
| **논리 백업** | pg_dump / pg_restore | 버전 간 이식, 테이블 단위 복구, 정의·권한·RLS 정책 포함 | 큰 DB는 느림, 덤프 시점만 복구 |
| **물리 백업** | pgBackRest, Barman, 스토리지 스냅샷 | 빠름, 대용량 | 같은 메이저 버전 필요 |
| **PITR** | 물리 백업 + **WAL 아카이브** | **원하는 시각으로** 되돌림 → RPO 분·초 단위 | 구성·저장 공간 |

**WAL (Write-Ahead Log)**: PostgreSQL은 데이터를 바꾸기 전에 변경 내용을 WAL에 먼저 기록한다. 이걸 계속 보관하면 "기준 백업 + 그 이후 WAL 재생"으로 특정 시각까지 복구할 수 있다.

**이 프로젝트에서는**: `pg_dump -Fc`(압축 커스텀 포맷)를 매일 MinIO에 저장하고 7개 보관했다. 덤프 507KB, 백업 Job 11초. RLS 테이블 때문에 **슈퍼유저로 덤프**했다(일반 계정은 정책에 막혀 일부 행만 보이거나 오류). 복구는 `pg_restore --clean --if-exists --single-transaction`으로 실패 시 전부 롤백되게 했고, RLS 정책 4개와 권한까지 함께 복구된 것을 확인했다.

**면접 한 줄**: "작은 DB는 pg_dump 논리 백업으로 충분하지만, RPO를 분 단위로 줄이려면 물리 백업과 WAL 아카이빙으로 PITR을 구성합니다."

## 8.4 3-2-1 원칙과 불변 백업

**3-2-1**: 사본 **3개**(원본 포함), 서로 다른 매체 **2종**, 그중 **1개는 다른 장소**(오프사이트). 최근에는 1개를 불변·오프라인으로, 복구 검증 오류 0을 더한 **3-2-1-1-0**도 말한다.

**불변 백업 (Immutable)**: 정해진 기간 동안 **관리자도 지우거나 바꿀 수 없게 잠근** 백업이다. 랜섬웨어는 운영 서버뿐 아니라 백업 서버의 관리자 계정까지 탈취해 백업을 지우는 경우가 많아서 필수다.
- MinIO **Object Lock (WORM)**: 객체 단위 보존 기간 잠금
- 엑사그리드: 랜섬웨어 복구 계층 + 삭제 지연(time-lock)
- Veeam: Hardened Repository (불변 리눅스 저장소)

**이 프로젝트의 한계**: 일반 버킷에 저장해서 불변 설정, 오프사이트 사본은 없다. 운영 전환 후속 과제로 기록했다.

**면접 한 줄**: "랜섬웨어는 백업까지 노리기 때문에, 3-2-1 원칙에 더해 관리자도 지울 수 없는 불변 저장소와 오프사이트 사본이 필요합니다."

## 8.5 "복구해 봐야 백업이다"

**왜**: 백업 파일이 쌓이고 있다는 것과 그걸로 서비스가 되살아난다는 것은 다르다. 권한, 확장 기능(pgvector), RLS 정책, 인덱스, 앱의 재연결까지 돌아와야 정상이다.

**복구 훈련 절차 (이 프로젝트)**
1. 사전 상태 기록(행 수, 서비스 응답)
2. 백업
3. 백업 이후 데이터 추가 (RPO 확인용 표식)
4. 장애 주입 (테이블 삭제) → **실제 질문으로 영향 확인(503)**
5. 최신 백업 복구
6. 행 수·정책·서비스 재확인, 표식이 사라졌는지 확인
7. RTO/RPO 계산, 보고서 자동 작성

**백업 성공 감시**: "실패" 알람만으로는 부족하다. 스케줄러가 멈추면 실패도 안 일어난다. 그래서 **"마지막 성공 후 24시간이 넘었다"**를 감시했다(데드맨 스위치와 같은 발상).

**면접 한 줄**: "백업은 복구 훈련까지 해야 백업이라서, 실제로 테이블을 지우고 복구해 시간과 잃은 데이터를 쟀고, 성공 신호가 끊기는 걸 감시합니다."
