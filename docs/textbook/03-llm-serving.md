# 3장. LLM 서빙: GPU 메모리, 양자화, KV 캐시, 성능 지표

> 관련: M2 서빙 · M9 사이징 · 노트 [02-llm-serving](../study/02-llm-serving.md), [09-sizing](../study/09-sizing.md)

## 3.1 LLM은 어떻게 답을 만드나: 토큰과 자기회귀 생성

**정의**: LLM(대형 언어 모델)은 지금까지의 글을 보고 **다음 토큰 하나의 확률**을 계산해 고르는 일을 반복해서 문장을 만든다. 이를 **자기회귀(autoregressive) 생성**이라 한다.

**토큰**: 모델이 글을 다루는 단위로, 단어 조각이다. 영어는 대략 단어의 3/4, 한국어는 한 글자~몇 글자 정도가 한 토큰이다. "컨텍스트 4,096"은 질문·참고 문서·답변을 합쳐 4,096토큰까지 본다는 뜻이다.

**동작 원리 — 두 단계**
1. **프리필(prefill)**: 입력(프롬프트) 전체를 한 번에 읽어 각 토큰의 중간 결과(K, V)를 계산한다. 입력이 길수록 오래 걸린다 → **첫 토큰까지 시간(TTFT)**을 좌우한다.
2. **디코드(decode)**: 토큰을 하나씩 만든다. 토큰 하나마다 **모델 가중치 전체를 메모리에서 읽어야** 해서 메모리 대역폭이 병목이다 → **토큰/초**를 좌우한다.

**이 프로젝트에서는**: CPU 추론에서 단독 요청 15.9토큰/초, 동시 4개 요청당 10.5토큰/초였다. RAG로 근거 문서를 넣으면 프롬프트가 길어져 TTFT가 늘어난다.

**면접 한 줄**: "LLM은 프롬프트를 한 번에 읽는 프리필과 토큰을 하나씩 만드는 디코드로 나뉘고, 각각 TTFT와 토큰/초를 좌우합니다."

## 3.2 파라미터와 가중치 메모리

**정의**: 파라미터는 모델이 학습으로 익힌 숫자들이다. 3B는 30억 개, 70B는 700억 개다. 이 숫자들을 메모리에 올린 것이 **가중치**다.

**공식**: **가중치 메모리 = 파라미터 수 × 파라미터당 바이트**
| 정밀도 | 바이트 | 7B | 32B | 70B |
|---|---|---|---|---|
| FP32 | 4 | 28GB | 128GB | 280GB |
| FP16 / BF16 | 2 | **14GB** | 64GB | 140GB |
| FP8 / INT8 | 1 | 7GB | **32GB** | 70GB |
| INT4 | 0.5 | 3.5GB | 16GB | 35GB |

**이 프로젝트에서는**: qwen2.5:3b Q4_K_M 파일이 1.9GB였다(3.1B × 평균 약 0.6바이트). 사이징 계산기 테스트로 "7B FP16 = 14GB"를 고정했다.

**흔한 오해**: "모델 파일 크기만큼 GPU가 있으면 된다" → 가중치는 시작일 뿐이다. **KV 캐시와 여유분**이 더 필요하다(3.4절).

**면접 한 줄**: "가중치 메모리는 파라미터 수 곱하기 파라미터당 바이트라서 7B FP16은 약 14GB입니다."

## 3.3 양자화 (Quantization)

**정의**: 파라미터 하나를 표현하는 비트 수를 줄여(16비트 → 8비트 → 4비트) 모델을 작게 만드는 기술이다.

**왜 필요한가**: 메모리가 줄면 ① 같은 GPU에 더 큰 모델을 올리거나 ② 남는 메모리를 KV 캐시에 써서 동시 사용자를 늘릴 수 있다. 디코드는 메모리 대역폭이 병목이라, 읽을 바이트가 줄면 **속도도 대체로 빨라진다.**

**동작 원리**: 넓은 범위의 실수를 작은 정수 범위로 대응시키고, 블록마다 **스케일 값**을 함께 저장해 되돌린다. 정보가 일부 손실되므로 정확도가 조금 떨어질 수 있다.
- **FP8**: 8비트 부동소수점. Hopper(H100·H200)·Ada(L40S)가 하드웨어로 지원. 손실이 작다. **A100은 FP8 연산 미지원**.
- **INT8 / INT4**: 정수 양자화. GPTQ, AWQ 같은 방법은 중요한 가중치를 보호해 손실을 줄인다.
- **GGUF Q4_K_M**(Ollama/llama.cpp): 블록마다 정밀도를 다르게 하는 4비트 계열 방식.

**흔한 오해**: "양자화하면 무조건 성능이 나빠진다" → FP8은 대부분 차이가 작다. 다만 INT4에서는 한국어·전문 용어·긴 추론에서 차이가 보일 수 있다. **고객 질문 세트로 비교해서 정한다.**

**면접 한 줄**: "양자화는 메모리와 속도를 얻고 정확도를 조금 내주는 트레이드오프라서 FP16·FP8·INT4를 같은 질문 세트로 비교해 결정합니다."

## 3.4 KV 캐시

**정의**: 모델이 앞에서 읽은 토큰들의 중간 계산 결과(Key, Value)를 저장해 두는 메모리다. 다음 토큰을 만들 때 앞부분을 다시 계산하지 않기 위해 쓴다.

**왜 필요한가**: KV 캐시가 없으면 토큰 하나를 만들 때마다 앞의 모든 토큰을 처음부터 다시 계산해야 해서, 답이 길어질수록 엄청나게 느려진다.

**공식**: **KV 캐시 = 2(K와 V) × 레이어 수 × KV 헤드 수 × 헤드 차원 × 바이트 × 컨텍스트 길이 × 동시 요청 수**
- qwen2.5:3b: 2 × 36 × 2 × 128 × 2바이트 = **토큰당 약 36KB** → 4,096토큰 × 4슬롯 ≈ **0.6GB**
- 32B급(64레이어, KV헤드 8): 토큰당 약 262KB → 4,096 × 30건 ≈ **32GB**

**GQA(Grouped Query Attention)**: 질의 헤드 여러 개가 KV 헤드 하나를 공유하게 해서 KV 헤드 수를 줄인다. 최근 모델 대부분이 써서 KV 캐시를 크게 아낀다(qwen2.5:3b는 KV 헤드가 2개).

**PagedAttention**(vLLM): KV 캐시를 운영체제의 페이지처럼 작은 블록으로 나눠 필요한 만큼만 할당한다. 미리 최대 길이만큼 잡아 두는 낭비를 줄여 **동시 처리량을 크게 높인다.**

**이 프로젝트에서는**: M9 RFP 사이징에서 32B FP8의 가중치(32.0GB)와 동시 30건의 KV 캐시(32.2GB)가 거의 같았다. **GPU 대수를 결정하는 건 모델 크기보다 동시성과 컨텍스트**라는 핵심 발견이다.

**면접 한 줄**: "KV 캐시는 컨텍스트 길이와 동시 요청에 비례해 커져서, 사용자가 늘면 모델이 들어가도 GPU가 모자라게 됩니다."

## 3.5 성능 지표: TTFT, 토큰/초, 처리량, 백분위

| 지표 | 정의 | 무엇이 좌우하나 |
|---|---|---|
| **TTFT** (Time To First Token) | 요청 후 첫 토큰까지 시간 | 프롬프트 길이(프리필), **대기열** |
| **TPOT / 토큰/초** | 첫 토큰 이후 생성 속도 | 메모리 대역폭, 모델 크기, 동시 배치 |
| **처리량 (Throughput)** | 서버 전체 초당 생성 토큰 | 배치 크기, 동시성 |
| **p50 / p95 / p99** | 100건 중 50·95·99번째로 느린 값 | 평균은 느린 소수 요청을 숨긴다 |

**동시성의 효과 (이 프로젝트 실측, CPU)**
| 동시 요청 | 요청당 토큰/초 | 총 처리량 | TTFT p95 |
|---|---|---|---|
| 1 | 15.9 | 15.7 | 0.12s |
| 4 | 10.5 | **34.8 (2.2배)** | 2.5s |
| 8 | 9.2 | 36.3 (포화) | **13.0s** |

해석: 동시 4개까지는 한 번에 묶어 계산하는 **배치 효과**로 처리량이 오른다. 슬롯(4개)을 넘으면 나머지는 **대기열**에서 기다려 TTFT가 폭증한다. M6에서 동시 6개를 보냈을 때 대기열 5 → TTFT p95 약 1분이 대시보드에 그대로 나타났다.

**면접 한 줄**: "사용자 체감은 TTFT p95로 보고, 동시 요청이 처리 슬롯을 넘으면 대기열 때문에 TTFT가 먼저 무너집니다."

## 3.6 서빙 엔진

| 엔진 | 특징 | 적합한 곳 |
|---|---|---|
| **Ollama** | 설치가 쉽고 CPU에서도 동작, GGUF 양자화 모델 | 개발·소규모·이 프로젝트 |
| **vLLM** | PagedAttention, **continuous batching**(요청이 끝나는 대로 새 요청을 배치에 끼움), OpenAI 호환 API | 운영 LLM 서빙의 표준에 가까움 |
| **TensorRT-LLM / Triton** | NVIDIA 최적화 커널, 여러 종류 모델 동시 운영 | 최고 성능, 비전·음성 모델 혼합 |

**OpenAI 호환 API**: `/v1/chat/completions` 같은 같은 형식을 지원하면 엔진을 바꿔도 앱 코드를 고치지 않는다. 이 프로젝트 벤치마크 스크립트가 이 형식을 써서 Ollama와 vLLM 모두에 쓸 수 있다(vLLM은 미검증).

**면접 한 줄**: "개발은 Ollama로도 충분하지만, 운영에서 동시 사용자를 받으려면 continuous batching과 PagedAttention이 있는 vLLM 같은 엔진이 필요합니다."

## 3.7 임베딩 모델

**정의**: 문장을 고정 길이 숫자 목록(벡터)으로 바꾸는 모델이다. 뜻이 비슷한 문장은 가까운 벡터가 된다. bge-m3는 1024개 숫자(1024차원)로 바꾼다.

**동작 원리**: 문장을 토큰으로 나눠 트랜스포머로 처리한 뒤 하나의 벡터로 요약한다. 두 벡터의 **코사인 유사도**(방향이 얼마나 같은가)로 의미의 가까움을 잰다.

**이 프로젝트에서는**: "E-203 유압 압력 저하" ↔ "유압이 떨어졌을 때 조치" 유사도 0.570, ↔ "점심 메뉴 추천" 0.254. M8에서 생성 모델(qwen2.5:3b)을 임베딩에 쓰려 하자 **501(미지원)**이었고, 1024차원 문서에 768차원 질문 벡터로 검색하면 `different vector dimensions 1024 and 768`로 거부됐다.

**흔한 오해**: "임베딩 모델만 바꾸면 검색이 좋아진다" → 문서와 질문은 **반드시 같은 모델**로 임베딩해야 한다. 바꾸면 전체 문서를 다시 임베딩해야 한다.

**면접 한 줄**: "임베딩 모델은 문장을 의미 좌표로 바꾸는 모델이고, 문서와 질문을 같은 모델로 임베딩해야 검색이 됩니다."
