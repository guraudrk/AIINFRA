# 1장. 리눅스·컨테이너·GPU 소프트웨어 스택

> 관련: M0 환경 점검 · 노트 [00-environment](../study/00-environment.md)

## 1.1 운영체제와 커널

**정의**: 운영체제(OS)는 CPU·메모리·디스크·네트워크 같은 하드웨어를 관리하고, 그 위에서 프로그램이 실행되도록 해 주는 기본 소프트웨어다. 그 핵심부가 **커널**이다. 커널은 "어떤 프로세스가 언제 CPU를 쓸지", "메모리를 어디에 줄지", "어느 장치에 어떻게 접근할지"를 결정한다.

**왜 필요한가**: 프로그램이 하드웨어를 직접 다루면 서로 충돌하고 보안이 무너진다. 커널이 중재자 역할을 해서 여러 프로그램이 안전하게 같은 하드웨어를 나눠 쓴다.

**동작 원리**
1. 프로그램은 **사용자 공간(user space)**에서 돌고, 하드웨어 접근이 필요하면 **시스템 콜**(예: 파일 열기, 메모리 요청)로 커널에 부탁한다.
2. 커널은 **커널 공간**에서 요청을 검사하고 실행한 뒤 결과를 돌려준다.
3. 장치마다 **드라이버**(커널 모듈)가 있어서 커널이 그 장치와 대화할 수 있다. GPU 드라이버도 그중 하나다.

**이 프로젝트에서는**: Windows 위에 WSL2로 리눅스 커널(6.18)을 띄우고 Ubuntu 26.04를 썼다. 쿠버네티스, 컨테이너, 셸 스크립트는 모두 리눅스 기준이다.

**흔한 오해**: "리눅스 = Ubuntu"가 아니다. 리눅스는 커널이고, Ubuntu·RHEL은 그 커널에 도구를 묶은 **배포판**이다. 고객사 서버는 기술 지원 계약이 있는 RHEL을 쓰는 경우가 많다.

**실무 포인트**: GPU 드라이버는 커널 버전에 맞춰 빌드되는 커널 모듈이라, **커널을 업데이트하면 드라이버가 깨질 수 있다.** 그래서 GPU 서버는 커널·드라이버 버전을 함께 고정하고 업데이트를 계획적으로 한다.

**면접 한 줄**: "커널은 하드웨어를 프로그램들에게 안전하게 나눠 주는 중재자이고, GPU 드라이버는 그 커널에 붙는 모듈이라 커널과 버전을 함께 관리해야 합니다."

## 1.2 가상 머신(VM)과 하이퍼바이저

**정의**: 가상 머신은 한 대의 물리 서버 안에 **OS를 통째로 하나 더 띄운 가짜 컴퓨터**다. 하이퍼바이저(VMware ESXi, KVM, Hyper-V)가 CPU·메모리·디스크를 가상으로 쪼개 각 VM에 나눠 준다.

**왜 필요한가**: 서버 한 대에 여러 업무를 격리해서 돌리고, 하드웨어 고장 시 다른 서버로 옮기는 등 자원 활용과 운영 유연성을 높인다.

**동작 원리**
1. 하이퍼바이저가 하드웨어 위(또는 호스트 OS 위)에서 돈다.
2. 각 VM에는 **게스트 OS와 그 OS의 커널**이 따로 있다.
3. 게스트가 하드웨어를 건드리면 하이퍼바이저가 가로채 실제 하드웨어에 대신 전달한다(CPU 가상화 확장 VT-x/AMD-V가 이를 빠르게 해 줌).

**이 프로젝트에서는**: WSL2 자체가 Hyper-V 위의 경량 VM이다. 그 안에서 Docker와 kind가 돈다.

**흔한 오해**: "VM은 느리다"는 옛말이다. 하드웨어 가상화 지원으로 CPU 성능 손실은 작다. 다만 OS를 통째로 띄우므로 **메모리와 기동 시간**이 컨테이너보다 크다.

**실무 포인트**: GPU를 VM에 줄 때는 **패스스루**(GPU 한 장을 VM 하나에 통째로) 또는 **vGPU**(NVIDIA 라이선스로 GPU를 쪼개 여러 VM에)를 쓴다. 쿠버네티스를 베어메탈에 올리면 이 가상화 계층이 없어 GPU를 직접 쓴다.

**면접 한 줄**: "VM은 하드웨어를 가상화해 OS를 통째로 하나 더 띄우는 방식이고, 컨테이너는 커널을 공유하며 프로세스만 격리하는 방식입니다."

## 1.3 컨테이너: namespace와 cgroup

**정의**: 컨테이너는 **호스트 커널을 공유하면서, 프로세스가 보는 세상(파일, 네트워크, 프로세스 목록)을 격리하고, 쓸 수 있는 자원을 제한한** 프로세스 묶음이다.

**왜 필요한가**: "내 PC에서는 되는데 서버에서는 안 돼요" 문제를 없앤다. 프로그램과 필요한 라이브러리를 **이미지**로 묶어 어디서나 똑같이 실행한다. VM보다 가볍고 빨리 뜬다(초 단위).

**동작 원리** — 리눅스 커널 기능 두 가지가 핵심이다.
1. **namespace (격리, "무엇이 보이는가")**
   - PID: 컨테이너 안에서는 자기 프로세스만 보이고, 첫 프로세스가 1번
   - Network: 자기만의 네트워크 인터페이스·IP·포트
   - Mount: 자기만의 파일 시스템 루트
   - UTS(호스트 이름), IPC, User 등
2. **cgroup (제한, "얼마나 쓸 수 있는가")**
   - CPU: 쓸 수 있는 CPU 시간 상한 → 넘으면 **잠깐씩 멈춤(throttling)**
   - 메모리: 쓸 수 있는 메모리 상한 → 넘으면 커널의 **OOM Killer가 프로세스를 강제 종료**
3. **이미지**: 여러 층(layer)으로 쌓인 읽기 전용 파일 묶음. 컨테이너가 뜨면 맨 위에 쓰기 가능한 얇은 층이 하나 붙는다(overlay 파일 시스템).

**이 프로젝트에서는**
- kind는 쿠버네티스 **노드 자체를 Docker 컨테이너로** 띄운다. 그래서 PC 한 대에 노드 4대를 만들 수 있었다.
- M6에서 Grafana의 CPU limit(500m)에 걸려 **throttling**으로 API가 멈춘 것, M8에서 메모리 limit(512Mi)을 넘어 **OOMKilled(Exit 137)**가 난 것 모두 cgroup의 동작이다.

**흔한 오해**
- "컨테이너는 작은 VM이다" → 아니다. **커널을 공유**한다. 그래서 커널 취약점은 모든 컨테이너에 영향을 줄 수 있고, 리눅스 컨테이너는 리눅스 커널에서만 돈다.
- "CPU limit 넘으면 죽는다" → 아니다. **메모리 초과는 죽고, CPU 초과는 느려진다.**

**실무 포인트**: 운영 환경의 컨테이너 런타임은 Docker가 아니라 **containerd**나 **CRI-O**(OpenShift)다. Docker는 개발 도구로 많이 쓰고, 쿠버네티스는 CRI라는 표준 인터페이스로 런타임과 대화한다.

**면접 한 줄**: "컨테이너는 namespace로 보이는 범위를 격리하고 cgroup으로 쓸 수 있는 자원을 제한한 프로세스입니다. 메모리 limit을 넘으면 OOMKilled로 죽고, CPU limit을 넘으면 throttling으로 느려집니다."

## 1.4 GPU와 GPU 소프트웨어 스택

**정의**: GPU는 단순한 계산을 **수천 개의 코어로 동시에** 처리하는 칩이다. AI 모델 계산의 대부분은 거대한 행렬 곱셈이라 GPU가 CPU보다 수십~수백 배 빠르다.

**왜 필요한가**: LLM은 답을 한 글자(토큰) 낼 때마다 수십억 개 파라미터를 메모리에서 읽어 곱한다. 이때 병목은 계산량과 **메모리 대역폭**이다. GPU는 고대역폭 메모리(HBM, GDDR)와 대량 병렬 코어로 이를 해결한다.

**동작 원리 — 소프트웨어 3층**
1. **드라이버**(커널 모듈, 예: 591.86): OS가 GPU를 인식하고 명령을 보낼 수 있게 한다. `nvidia-smi`가 드라이버를 통해 GPU 상태를 읽는다.
2. **CUDA**(사용자 공간 라이브러리, 예: 12.4): 프로그램이 GPU에 계산을 시키는 도구 모음. 보통 **컨테이너 이미지 안**에 들어 있다.
   - 호환 규칙: **드라이버가 지원하는 최대 CUDA 버전 ≥ 이미지의 CUDA 버전**이어야 한다. `nvidia-smi` 오른쪽 위 "CUDA Version"이 드라이버가 지원하는 최대치다.
3. **NVIDIA Container Toolkit**: 컨테이너를 만들 때 호스트의 GPU 장치 파일(`/dev/nvidia*`)과 드라이버 라이브러리를 컨테이너 안에 넣어 준다. 이게 있어야 `docker run --gpus all`이 동작한다.

**이 프로젝트에서는**
- RTX 4060 8GB에서 `docker run --gpus all nvidia/cuda:12.4.1-base ... nvidia-smi`로 **컨테이너 안 GPU 인식**을 확인했다(드라이버 CUDA 13.1 ≥ 이미지 12.4).
- 그런데 Windows 화면이 VRAM 5.2GB를 쓰고 있어서 여유는 약 3GB였다 → 모델을 3B로 정한 근거.
- kind 노드 안까지 GPU를 넘기는 건 WSL2 구조(`/dev/dxg`)상 불안정해서 **SIMULATED**(장부상 GPU 등록)로 진행했다.

**흔한 오해**: "CUDA를 서버에 설치해야 한다" → 컨테이너 환경에서는 **호스트에는 드라이버만**, CUDA는 이미지 안에 둔다. 그래서 같은 서버에서 CUDA 11과 12 앱을 동시에 돌릴 수 있다.

**실무 포인트 — 데이터센터 GPU 서버 구축 순서**
1. 랙 실장, 이중화 전원, 케이블링 (랙당 전력·냉각 한도 확인: GPU 서버는 대당 수 kW)
2. **BMC**(Dell iDRAC, HPE iLO) 관리망 연결 → 원격 전원·콘솔·펌웨어 업데이트
3. OS 설치 (폐쇄망이면 내부 패키지 저장소)
4. 드라이버 → (멀티 GPU면 Fabric Manager) → Container Toolkit, 또는 **GPU Operator**가 이걸 자동화
5. 쿠버네티스/OpenShift + GPU Operator(드라이버, device plugin, DCGM exporter)
6. 모니터링, 7. 인수 테스트(`nvidia-smi`, `dcgmi diag`, 부하 테스트)

**면접 한 줄**: "GPU 컨테이너는 호스트 드라이버, 이미지 안의 CUDA, 둘을 연결하는 Container Toolkit 세 층으로 동작하고, 드라이버가 이미지의 CUDA 버전 이상을 지원해야 합니다."

## 1.5 WSL2와 Docker Desktop

**정의**: WSL2는 Windows 안에서 진짜 리눅스 커널을 경량 VM으로 돌리는 기능이다. Docker Desktop은 Windows에서 Docker를 쓰게 해 주는 프로그램으로, 내부적으로 **docker-desktop이라는 별도 WSL 배포판**에서 Docker 엔진을 돌린다.

**동작 원리**: Ubuntu 배포판 안의 `docker` 명령은 "리모컨"이고, 실제 엔진은 docker-desktop 배포판에 있다. **WSL Integration**을 켜면 Ubuntu에 그 엔진으로 연결된 docker CLI와 소켓(`/var/run/docker.sock`)이 생긴다.

**이 프로젝트에서 겪은 것**
- `wsl --shutdown`으로 메모리 설정을 바꿨더니 docker-desktop 배포판까지 꺼져 kind가 "docker를 찾을 수 없다"며 실패했다 → Docker Desktop 재시작.
- 공개 이미지를 받는데 Windows 자격 증명 도우미(`desktop.exe`) 호출이 WSL interop(vsock) 시간 초과로 실패했다 → 빈 `DOCKER_CONFIG`로 익명 pull.
- Docker Desktop은 **containerd 이미지 저장소**를 써서, `docker save`가 멀티 아키텍처 목차 전체를 저장했다(6장 폐쇄망 참고).

**면접 한 줄**: "WSL2는 실제 리눅스 커널이라 쿠버네티스 도구는 서버와 같지만, GPU와 Docker 엔진이 Windows 쪽 구성요소를 거치기 때문에 하드웨어 계층은 실제 서버와 다릅니다."
